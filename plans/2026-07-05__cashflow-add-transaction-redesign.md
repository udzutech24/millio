## 0. TL;DR находок исследования

Прежде чем спорить про архитектуру — важный факт: **часть идей уже частично реализована в коде**, просто не доведена до конца или не переиспользована в нужном месте. Это сильно снижает риск и объём работы.

| Идея | Готовность инфраструктуры |
|------|---------------------------|
| #1 Объединить Доход/Расход в один шит | **~70% готово.** `CashflowCategorySheetContainer` (файл `CashflowCategorySheetContainer.swift`) уже реализует Monzo-style свайп-контейнер с сегмент-пикером Расходы\|Доходы\|Всё, используется как `.sheet` при добавлении дохода/расхода в `CashflowView.swift:242-244`. Не хватает: 3-й таб сейчас — "Всё" (браузинг истории), а не "Перевод". Transfer живёт отдельным шитом (`CashflowTransferTransactionSheet` → напрямую `CashflowTransactionEditorView`, `CashflowOperationSheets.swift:1501-1512`). |
| #2 Избранные категории вместо полной сетки | **Инфраструктура на 90% готова.** Уже есть ручной pin (`CashflowCategoryPinPrefs.swift`), custom order (`CashflowCategoryOrderPrefs.swift`), pin/unpin через long-press overlay (`CashflowCategoryActionOverlay`, `CashflowOperationSheets.swift:308-343`), `orderedCategoryOptions()` кладёт pinned первыми. Частотного трекинга использования (usageCount/lastUsedAt) **нет нигде** — его придётся либо строить с нуля, либо не строить вообще (см. решение ниже). Сейчас сетка **всегда** показывает все категории (`categories` computed var, `CashflowOperationSheets.swift:172-177`, `categoriesSection` `LazyVGrid`, строка 756+) — до 128 case в `ExpenseCategoryCatalog.swift`, реально пользователь создаёт куда меньше. |
| #3 Вынести бюджет-прогресс из формы | **Готовый неиспользуемый компонент есть.** `BudgetHeroCard.swift` существует, но **нигде не подключён** (grep не находит вызовов вне своего файла — мёртвый код). Логика расчёта `monthlyBudgetSummary(for:month:in:)` — чистый async-метод на `CashflowViewModel` (`CashflowViewModel+History.swift:187`), уже не завязан на UI шита. Сейчас снапшот бюджета — `@State` внутри `CashflowCategoryTransactionSheet` (`CashflowOperationSheets.swift:107-111`), считается в `.task`/`.onAppear` только пока форма открыта. |
| #4 Сжать breakdown-список на главном экране | **Наполовину готово.** `assetBreakdownSection` в `CashflowView.swift` (`CashflowContentView`, строки ~361-468) уже **сворачиваемая** (`expandableStatRow` + `@State showIncomeBreakdown/showExpenseBreakdown`, по умолчанию `false`). Но при разворачивании `breakdownList()` (строка 527+) рендерит **полный** список категорий без ограничения и без ссылки на Историю. |
| Доп. трек: авто-транзакции вкладов/кредитов (§1.8) | **Вклады закрыты в Фазе 0 (см. ниже).** Кредиты сознательно отложены — отдельный дизайн-цикл (нет ни recurring-механизма, ни планировщика на стороне AccountsCore). |

Вывод: все 4 идеи технически дешевле, чем казалось на этапе концепта — переиспользуем существующую инфраструктуру, а не строим с нуля. Это меняет оценку рисков в лучшую сторону, но не отменяет edge cases ниже. Отдельно — обнаружен и включён в план сломанный/недостающий механизм авто-транзакций от финансовых продуктов (§1.8), который чинится ДО визуального редизайна (Фаза 0).

## 1. Текущая архитектура (по каждому пункту)

### 1.1 Точки входа в добавление транзакции — их ДВЕ, не одна

- **Таб Cashflow** (`CashflowView.swift`, `CashflowContentView`): кнопки Доход/Расход/Перевод (`actionButtonsSection`, строки 309-357) вызывают `viewModel.handle(.addTransaction(kind))`, что выставляет `state.creatingTransactionType`. Презентация — единый `.sheet` (строки 230-254), свитчащийся по типу:
  - `.income` → `CashflowCategorySheetContainer(initialTab: .incomes)`
  - `.expense` → `CashflowCategorySheetContainer(initialTab: .expenses)`
  - `.transfer` → `CashflowTransferTransactionSheet` (отдельный, полный editor)
- **Dashboard FAB** (`UI/Main/RootTabView.swift`, строки 107-121): три **независимых** `.sheet` через `showIncomeSheet`/`showExpenseSheet`/`showTransferSheet`, вызывающие **старые** отдельные `CashflowIncomeTransactionSheet` / `CashflowExpenseTransactionSheet` (`CashflowOperationSheets.swift:58,76` — тонкие обёртки над `CashflowCategoryTransactionSheet`, НЕ через контейнер) / `CashflowTransferTransactionSheet`.

**Важно:** Dashboard FAB и Cashflow-таб уже сейчас показывают технически разные шиты для дохода/расхода (обёртка `CashflowIncomeTransactionSheet` vs контейнер `CashflowCategorySheetContainer`), хотя оба в итоге рендерят один и тот же `CashflowCategoryTransactionSheet`. Разница — наличие свайп-переключателя. Задача фиксирует скоуп только на Cashflow-таб, но это расхождение UX между двумя точками входа нужно явно обозначить владельцу (см. §3, риск R1).

### 1.2 Общая форма Income/Expense — `CashflowCategoryTransactionSheet`

`CashflowOperationSheets.swift:94-1499` (1.4k строк одного `struct`). Внутри:
- `headerSection`, `monthlyTotalSection`, `managementSection` (recurring/planned/settings/bulk-import входы)
- `categoriesSectionHeader` (кнопка Sort/Edit order) + `categoriesSection` (`LazyVGrid` по `categories` — **все** `orderedCategoryOptions(kind, matching: searchText)`, без лимита)
- `monthlyBudgetInlineSection` (строка 566+) — бюджет-прогресс **встроен в форму**, видим только пока шит открыт
- long-press → `CashflowCategoryActionOverlay` (pin/unpin, edit, delete, "операции")
- tap по категории → `navigationDestination(item: $selectedCategory)` → полноценный `CashflowTransactionEditorView` (recurrence, валюта, счета и т.д. — не трогаем)
- tap по плитке (короткий) → `quickEntryCategory` → `CashflowQuickEntrySheet` (быстрый ввод суммы)

### 1.3 Категории — источник данных

- `CashflowViewModel+Categories.swift` — тонкие проброски к `CashflowCategoryService` (`CashflowCategoryService.swift`, 1217 строк — сервис, не VM, декомпозиция уже сделана правильно).
- Pin: `CashflowCategoryPinPrefs` — `UserDefaults`, ключ `cashflow.category_pins.<kind>`, набор raw-values.
- Order: `CashflowCategoryOrderPrefs` — `UserDefaults`, ключ `cashflow.category_order.<kind>`, массив raw-values (drag-reorder через `CashflowCategoryReorderSheet`).
- Сортировка: `CashflowCategoryService.sortCategoryOptions(options, pinnedRawValues:)` — pinned первыми (порядок среди pinned и custom order — надо перепроверить точную реализацию сервиса при кодировании фазы 2, сейчас за скобками research).
- **Частота использования категории нигде не считается.** Ни `usageCount`, ни `lastUsedAt` не существует ни в модели, ни в сервисе.

### 1.4 Бюджет

- Модели: `BudgetPlan` (`Budget/BudgetPlan.swift`, `Persistable`/SwiftData), `BudgetCategoryLimit` (`Budget/BudgetCategoryLimit.swift`).
- Расчёт: `BudgetProgressCalculator.swift` → строит `BudgetProgressSnapshot` (`BudgetProgressModels.swift`).

- Настройка лимитов: `BudgetSetupSheet.swift` (570 строк) — открывается из `CashflowCategoryTransactionSheet` (`showBudgetSetupSheet`), это остаётся как есть.

### 1.5 Breakdown на главном экране Cashflow

- `CashflowContentView.assetBreakdownSection` (`CashflowView.swift:361-468`) — уже card-based UI со статьями "Активы на начало", "Доходы" (сворачиваемая), "Изменение стоимости активов", "Расходы" (сворачиваемая), "Активы на конец", "Итог".
- `breakdownList()` (строка 527+) рендерит `viewModel.state.incomeBreakdown` / `expenseBreakdown` (тип `[CashflowCategoryBreakdownEntry]`) **полностью**, без top-N, без ссылки в Историю.
- Полная история — `CashflowTransactionsHistoryView` (`CashflowTransactionsHistoryView.swift`, уже доступна через `.sheet` `showTransactionsHistory` в этом же `CashflowContentView`, строки 261-271).

### 1.6 Перевод (Transfer) — структурно другая форма

`CashflowTransferTransactionSheet` — тонкая обёртка, сразу открывающая `CashflowTransactionEditorView(transactionType: .transfer, showsTransactionTypeSection: false, ...)`. У Transfer **нет** сетки категорий, **нет** бюджета, **есть** выбор счёт-источник/счёт-получатель, конвертация валют при разных валютах счетов (см. `CashflowTransferExchangeRateMode` в `CashflowTransactionEditorView.swift:16`). Это полноценный сложный editor, а не "быстрый" flow, как Income/Expense.

### 1.7 Счета и валюта в быстром flow — подтверждённая дыра (проверено по требованию владельца)

Владелец поднял вопрос: не потеряется ли выбор счёта/валюты в едином быстром шите. Проверка кода подтверждает — **проблема реальна уже сейчас**, до всякого редизайна:

- `CashflowQuickEntrySheet.swift` (быстрый ввод суммы по тапу на плитку категории) **уже имеет** выбор счёта — `cardPicker` (строки 191-239), `@State selectedCardID`, дефолт на первую доступную карту при открытии (строка 97: `selectedCardID = viewModel.state.availableCards.first?.cardUniqueID`). Меню показывает список `viewModel.state.availableCards` + опцию "без карты".
- **Но валюта в этом sheet захардкожена**: `saveTransaction()` строит `CashflowTransaction(..., currency: viewModel.state.displayCurrency, ...)` (строка 296) — валюта транзакции всегда равна текущей валюте отображения приложения, **независимо от выбранного счёта**. Нет привязки currency→card, нет UI для смены валюты, нет вызова `CashflowCurrencySelectorView`.
- Для сравнения, полный `CashflowTransactionEditorView` делает это правильно: у каждого счёта есть собственная валюта (`CashflowSelectableAccount.currency`, `CashflowSelectableAccount.swift:16`), при выборе `selectedCardID` валюта транзакции резолвится через `accountCurrency(for:)` (`CashflowTransactionEditorView.swift:935-939`, ищет карту в `state.availableCards` либо в `viewModel.newCoreAccountsForCashflowPicker()`), плюс отдельно живёт ручной currency-picker и конвертация (`CashflowCurrencySelectorView`, `CashflowTransferExchangeRateMode`) на случай мультивалютной карты или ручного оверрайда.
- **Вывод:** это не "давний осознанный компромисс", а недоделанный quick-flow — `CashflowQuickEntrySheet` изначально не предполагал мультивалютный сценарий. Редизайн Фазы 3 **обязан закрыть эту дыру**, а не унаследовать её молча — иначе владелец (который реально платит разными картами в разных валютах) потеряет данные о валюте операции при быстром вводе.

### 1.8 ФУНДАМЕНТ (отдельный трек по требованию владельца) — авто-транзакции от вкладов/кредитов сломаны

Владелец: при добавлении вклада должно автоматически создаваться повторяющееся НАЧИСЛЕНИЕ (доход) в дату выплаты процентов; при добавлении кредита — повторяющееся СПИСАНИЕ (расход) в дату платежа, строго в дату, не раньше/позже. По его словам, сейчас это сломано. Проверка кода подтверждает — **проблема реальна, но не одна, а минимум две разные, и корень разный для вкладов и кредитов.**

**A. Общий движок повторяющихся транзакций — сам по себе исправен.**
`CashflowScheduledService.generateRecurringTransactionsIfNeeded()` (`CashflowScheduledService.swift:244-340`) — это единственный механизм материализации recurring-шаблонов (`isRecurringTemplate`, `CashflowTransaction.swift:846-850`: `recurrenceRule != .none && (income|expense) && recurrenceSeriesID != nil`) в реальные датированные транзакции. Логика корректна и уже решает требование "точно в дату, догонять пропущенное":
- Идёт от `templateDate` вперёд по `recurrenceOccurrenceDate(...)`, генерируя **каждое** пропущенное вхождение с его **исторически верной датой** (`expectedDate`), а не датой "сегодня" — то есть если приложение не открывали 2 недели, при следующем запуске догенерируются все пропущенные месяцы/периоды с правильными датами, задним числом. Это уже соответствует требованию владельца по механике "исполнения по дате".
- Идемпотентно (проверка `existsInMonth` перед вставкой — не плодит дубликаты при повторных запусках).
- Дополнительно есть `applyDuePlannedTransactionsIfNeeded()` (строка 343+) — отдельный checkpoint-механизм (`UserDefaults`, ключ `cashflow_due_auto_apply_checkpoint_v1`) для применения balance-эффекта одноразовых плановых транзакций, которые перешли из "будущего" в "прошлое" пока приложение было закрыто — тоже correct catch-up по датам.
- **✅ ПОДТВЕРЖДЕНО В ФАЗЕ 0 (2026-07-05):** `generateRecurringTransactionsIfNeeded()` вызывается через `CashflowScheduledService.scheduleRecurringGeneration()` ← `CashflowViewModel.scheduleRecurringGeneration()` ← `CashflowViewModel.loadTransactions()`, который вызывается при каждой инициализации/перезагрузке ленты Cashflow (init VM, после сохранения транзакции, после смены категорий и т.д.). Мотор регулярно вызывается, вход подтверждён рабочим — это НЕ было проблемой.

**B. Вклады — ✅ ЗАКРЫТО В ФАЗЕ 0.**
- **Верификация (шаг 1 плана) подтвердила:** после мержа `feature/accounts-core` в `develop` (258295d, 2026-07-05) единственный актуальный путь создания вклада — `FinanceAddAccountView.createDepositAccountOnNewCore()` → `AccountsCoreService.createAccount(kind: .deposit, depositMeta:)` + `DepositInterestScheduler.regenerateFutureInterestEvents(...)`. Легаси `InvestmentViewModel.syncDepositIncome`/`Investment(isDeposit:)` из UI недостижим для НОВЫХ вкладов (гейт `editingInvestment == nil` в `FinanceAddAccountView.swift:590`), но продолжает работать для СТАРЫХ вкладов, заведённых до миграции (`editingInvestment != nil` ветка) — не тронут, не регрессирует.
- **Причина невидимости дохода подтверждена:** `DepositInterestScheduler` кладёт `AccountEvent(.interest)` в ledger AccountsCore, но `AccountsCoreCashflowBridge` синхронизирует только в одну сторону (Cashflow → ядро) — обратного пути не было. Начисленные проценты существовали в данных, но НИКОГДА не попадали в видимую ленту/бюджет/историю Cashflow.
- **Фикс:** новый класс `AccountsCoreDepositCashflowBridge` (`millio/UI/Services/Cashflow/AccountsCoreDepositCashflowBridge.swift`) — read-мост в обратную сторону. Подробности решения, реализации и тестов — в секции Фазы 0 ниже.

**C. Кредиты — механизма нет вообще, это не регрессия, а отсутствующая фича. ⏸️ ОТЛОЖЕНО В ФАЗЕ 0 (см. секцию Фазы 0 — обоснование).**
Проверка `CreditViewModel.swift`/`Credit.swift`/`CreditManager.swift` — никакого `recurrenceSeriesID`/recurring-шаблона для платежей по кредиту не создаётся. Связь с Cashflow — разовая `CashflowTransaction(transactionType: .creditDebtAdjustment, ...)`, создаваемая в ДВУХ местах *(поправлено проверкой 2026-07-05)*: `CreditViewModel.swift:490-503` (ручное редактирование остатка в форме кредита) и quick-edit-путь в `FinanceViewModel` — любые изменения этого потока должны покрыть оба сайта и не задеть кредитные карты (тот же тип транзакции, но с `cardID`).
**Дополнительно подтверждено в Фазе 0:** после мержа `feature/accounts-core` кредиты ТОЖЕ создаются через новое ядро (`createObligationAccountOnNewCore`, `.loan`/`.debt`, `LoanMeta`) — и на стороне `AccountsCore` для кредитов **нет вообще никакого аналога `DepositInterestScheduler`** (ни планировщика платежей, ни авто-амортизации). Это не read-мост, это фича с нуля в двух системах сразу (Core + Cashflow), см. секцию Фазы 0.

⚠️ **Ложная предпосылка снята проверкой:** reminder-уведомления по кредитам НЕ существуют — поля `paymentDayOfMonth`/`nextPaymentDate`/`reminderEnabled` собираются в UI и сохраняются в модель, но ни одно уведомление не планируется (`NotificationManager` про кредиты не знает). Если напоминания нужны — их тоже придётся строить, на «reminders уже работают» опираться нельзя.

⚠️ **Авто-амортизация уже существует ТОЛЬКО для легаси `Credit`:** остаток долга уменьшается автоматически со временем — аннуитетный пересчёт при каждом `loadCredits` через `remainingAmountAdjustment`, БЕЗ создания транзакций. У новых кредитов (`AccountsCore`, `.loan`/`.debt`) такого пересчёта нет вовсе (подтверждено в Фазе 0 — только UI-калькулятор ежемесячного платежа для отображения, не постоянный процесс). Новая генерация платёжных транзакций обязана согласоваться с ОБОИМИ мирами и не задвоить погашение там, где авто-амортизация всё же есть (легаси).

**Вывод:** для кредитов нужно строить механизм с нуля по аналогии с §B (recurring-шаблон `.expense` с `recurrenceSeriesID`, привязанный к `Credit`, датированный `nextPaymentDate`/`paymentDayOfMonth`), это не "починка", а новая фича, и трудозатратнее, чем фикс вкладов.

**D. Связь с редизайном (для владельца — почему пункт актуален именно в этом плане):** отдельно от причины поломки, у владельца есть требование сделать эти операции **видимыми, не чёрным ящиком** — секция "Предстоящие" на главном экране Cashflow (ближайшие авто-списания/начисления). Инфраструктура для этого частично есть: `CashflowScheduledTransactionsView.swift` уже умеет показывать recurring/planned записи (используется как отдельный экран через `managementSection`, не на главном экране) — можно переиспользовать её вычисления вхождений для компактного виджета-превью на `CashflowContentView`, а не строить новый расчёт "следующая дата" с нуля. **⏸️ НЕ РЕАЛИЗОВАНО в этой сессии** (см. секцию Фазы 0 — остаток).

#### 2.1.1 Обязательное требование владельца — счёт и валюта не урезаются в быстром flow

Реальный сценарий владельца: платит разными картами в разных валютах. Это значит, что в объединённом быстром экране (сумма + категория, тот путь, который заменит/дополнит `CashflowQuickEntrySheet`) выбор счёта списания и его валюты должен быть на **первом экране**, а не только в дропе в полный `CashflowTransactionEditorView`. §1.7 подтвердил, что сейчас это дыра даже в текущем quick-flow (валюта захардкожена на `displayCurrency`, не привязана к счёту) — редизайн обязан её закрыть, а не унаследовать.

**Переиспользуем существующую модель данных, не изобретаем новую:**
- `selectedCardID` + `viewModel.state.availableCards` — тот же паттерн, что уже в `CashflowQuickEntrySheet.cardPicker` (`CashflowQuickEntrySheet.swift:191-239`) и в полном редакторе.
- `CashflowSelectableAccount.currency` (`CashflowSelectableAccount.swift:16`) — у каждого счёта/карты уже есть собственное поле валюты, ничего нового заводить не нужно.
- `accountCurrency(for:)` — паттерн резолва валюты по выбранному счёту, уже реализован в `CashflowTransactionEditorView.swift:935-939` (ищет карту в `state.availableCards` либо `newCoreAccountsForCashflowPicker()`) — переносим этот же метод резолва в быстрый flow вместо хардкода `displayCurrency`.
- `CashflowCurrencySelectorView` — уже существующий компонент ручного выбора валюты (для мультивалютных карт, когда платёж не в валюте счёта по умолчанию) — переиспользуем как оверлей/шторку поверх компактного чипа, не пишем новый picker.

**Конкретный UX:**
- Под полем суммы (или сбоку от неё) — компактный **чип счёта**: иконка карты/счёта + название + маленький бейдж валюты (напр. "💳 Тинькофф Black · ₽"). Дефолт — последний использованный счёт для этого типа операции (расход/доход), если такого нет — основной счёт пользователя (`availableCards.first`, как уже сделано в quick entry сегодня).
- Тап по чипу открывает компактный список счетов (переиспользуем `Menu`/список из текущего `cardPicker`, только в чиповом визуальном оформлении, а не bordered-box).
- Валюта — **привязана к выбранному счёту автоматически** (через `accountCurrency(for:)`), обновляется сразу при смене счёта, никакого отдельного шага не требуется в 90% случаев (одна валюта на карту).
- Для мультивалютных карт — рядом с бейджем валюты в чипе маленькая disclosure-стрелка/tap-target, открывающая `CashflowCurrencySelectorView` для ручного оверрайда валюты конкретной операции (сценарий: карта в рублях, но платёж прошёл в USD по SWIFT/за рубежом) — это уже рабочий сценарий в полном редакторе, здесь просто даём к нему быстрый доступ без выхода в полный editor.
- Если пользователь меняет валюту вручную и она отличается от валюты счёта — сохраняем оба значения на транзакции (как уже делает полный редактор через `exchangeRate`/`exchangeRateCurrency`), никакого нового поля модели не создаём.

**Итог по риску:** после этой правки быстрый flow (единый шит с чипами суммы/категории/счёта) по функциональности сравнивается с полным редактором в части "счёт + валюта", просто в сжатом визуальном виде. Ничего не урезается — только переиспользуется тот же набор полей и методов в более компактной раскладке.

#### 2.1.2 Обязательное требование владельца — убрать двухслойность (мини-шит → большой шит)

Прямая жалоба владельца: «появляется какой-то мини-экран, потом появляется большой экран при расходах/доходах — всё лишнее, надо резать». Это жёсткое требование, не опция для обсуждения.

**Что именно резать (по факту из §1.2):** сейчас для расхода/дохода пользователь проходит ДО ДВУХ последовательных шитов подряд для простой траты:
1. `CashflowCategoryTransactionSheet` — сетка категорий (тап по плитке),
2. `CashflowQuickEntrySheet` — второй bottom sheet поверх (ввод суммы, заметка, карта),
3. если нужно что-то нестандартное (дата задним числом, повтор, перевод) — ещё и `CashflowTransactionEditorView` третьим слоем через `navigationDestination`.

**Целевой flow — один экран:** сумма (крупная клавиатура, на весь экран или большую его часть) + категория (избранные плитки, §2.2) + чип счёта/валюты (§2.1.1) — всё видно и редактируется на одном экране, без промежуточного bottom sheet. Подтверждение операции — одна кнопка ("Сохранить"), без обязательного перехода на второй экран.

**Что это значит технически:**
- `CashflowQuickEntrySheet` как отдельный **второй shit** упраздняется как обязательный шаг. Его поля (`amountText`, `note`, `selectedCardID`, `saveTransaction()`) переезжают в тот же экран, что и сетка категорий — либо в виде unified-компоновки (категория выбрана → под сеткой/поверх неё появляется поле суммы + чипы, без закрытия текущего sheet), либо категория и сумма показываются одновременно с самого начала (сумма всегда видна сверху, категория — сразу под ней). Конкретную раскладку (модальный "drawer снизу вверх" вместо второго `.sheet`, или single-page с анимацией фокуса на сумму) решает исполнитель на этапе кодирования Фазы 3, но результат обязан быть **одним modal-контекстом**, не二 последовательными `.sheet`.
- `CashflowTransactionEditorView` **остаётся**, но переходит в статус опциональной ветки — доступен через явную кнопку/ссылку "Ещё параметры" (дата задним числом, recurrence, заметка длиннее одной строки, перевод с ручной конвертацией). Это уже частично так и есть (`navigationDestination(item: $selectedCategory)`), просто теперь это **не единственный путь досохранения** — большинство операций (сумма + категория + счёт) сохраняются прямо с первого экрана, без обязательного захода в полный редактор.
- **Транзитного периода не будет.** Ранее в этом плане (Фаза 1, п.3) допускалась формулировка "оставить дублирование бюджет-блока внутри формы на переходный период" — это НЕ относится к текущему требованию (речь там про бюджет-виджет, не про количество шитов) и остаётся на усмотрение владельца по итогам Фазы 1. Но применительно именно к двухслойности мини-шит→большой-шит — переходного периода нет, режем сразу в Фазе 3, не оставляем старый `CashflowQuickEntrySheet` как parallel path "на всякий случай".

**Третий таб "Всё" (browse-history) в контейнере — убирается, не является опцией.** Это уже было заложено в §2.1 (замена `.all` на `.transfer`) как предложение по KISS; теперь фиксируем это как **прямое требование владельца**, а не как одну из архитектурных возможностей — он явно сказал, что не понимает назначение этого таба. Причина, по которой это безопасно (см. §2.1): browse-all и так дублирует уже существующий отдельный вход "История" на главном экране Cashflow, функциональность не теряется, только убирается лишняя точка входа.

### 2.2 Идея #2 — избранные категории вместо полной сетки

**Решение по "избранности":** брать вручную запиненные категории (`CashflowCategoryPinPrefs`), **не** строить трекинг частоты использования.

Почему не частотный трекинг:
1. Это новая модель данных/агрегация (нужен подсчёт транзакций по категории за N дней) — WHY-затраты несоразмерны задаче ("сжать сетку"), а pin-инфраструктура уже целиком готова и юзер уже умеет ей пользоваться (long-press → pin).
2. Частотный алгоритм добавляет неочевидное поведение ("почему эта категория вдруг наверху") — pin явный и предсказуемый (SOLID: одна четкая ответственность источника truth).
3. Если пользователь ещё не запинил ничего (новый юзер, пустой pin-set) — нужен fallback, см. ниже.

**Логика "top 6-8 избранных":**
- Если `pinnedRawValues(for: kind).count >= 6` → показываем все pinned (если 6-8, ровно их; если pinned больше 8 — верхние 8 по существующему порядку `orderedCategoryOptions`).
- Если pinned < 6 → дополняем до 6 первыми категориями из `orderedCategoryOptions` (custom order либо дефолтный каталог), которые ещё не в pinned, сохраняя относительный порядок.
- Если категорий вообще меньше 6 (у части income-каталогов может быть немного) — показываем все, без ссылки "Все категории".
- "Все категории" — по нажатию раскрывает **эту же** `categoriesSection` в полный `orderedCategoryOptions(kind, matching: searchText)` (просто снимаем cap, это уже готовая логика — задача не требует нового экрана).

**Новое:** только `@State private var showAllCategories: Bool = false` + computed var `visibleCategories: [CashflowCategoryOption]` (cap-логика описана выше) в `CashflowCategoryTransactionSheet`. Существующий search (`searchText`) при активации автоматически должен снимать cap (если юзер ищет — очевидно, что нужен весь список, иначе поиск бесполезен для категорий вне top-8).

**Что не трогаем:** `CashflowCategoryReorderSheet`, `CashflowCategoryActionOverlay` (pin/unpin остаётся тем же жестом), `CashflowCategoryOrderPrefs` — вся инфраструктура drag-reorder работает без изменений, просто на неё накладывается cap для дефолтного отображения.

### 2.5 Визуальное качество единого шита — планка "топовое финансовое приложение"

Требование владельца: не функционально-минимальный экран, а уровень визуального качества как в современных топовых финансовых приложениях (референс-направление — Revolut/N26/YNAB-класс паттернов, не копирование один в один). Это нужно заложить в план **сейчас**, чтобы на этапе кодирования Фазы 3 не свалиться в дефолтный SwiftUI `List`/`Form`.

**Иерархия типографики суммы:**
- Сумма — самый крупный и единственный доминирующий элемент экрана (не делить внимание с заголовком навигации). Использовать самый крупный доступный шаг `AppTypography` для суммы (моноширинный/табличный numeric style, если такой токен есть в `AppTypography.swift` — проверить при кодировании; если нет — обосновать добавление нового токена, а не хардкодить `Font.system(size:)`, что запрещено правилами проекта).
- Валюта — рядом с суммой, визуально второстепенна (меньший вес/размер, не соревнуется с цифрами).
- Категория/счёт/заметка — визуально ниже суммы по типографической иерархии (значимо мельче), т.к. это "детали", а сумма — "факт".

**Живой отклик при вводе:**
- Ввод суммы — крупная клавиатура (кастомная numpad-раскладка на весь низ экрана, как уже частично сделано в `CashflowQuickEntrySheet.amountField`, — переиспользовать существующий `AmountInputFormatter`, не писать новый парсер).
- Использовать `.contentTransition(.numericText())` при изменении суммы (паттерн уже используется в проекте, см. `CashflowView.swift` — `statRow`/`expandableStatRow` уже применяют `.contentTransition(.numericText())`) — переносим тот же приём на поле суммы в новом шите для "живого" ощущения роста цифр.
- Выбор категории/счёта — мгновенный визуальный отклик (плитка/чип подсвечивается сразу по тапу, через `AppAnimation`-токен, не самодельный `withAnimation(.easeInOut(duration: ...))` с хардкод-длительностью, если в `AppAnimation.swift` уже есть подходящий токен для такого отклика — использовать его).

**Категории/счета — чипы с иконкой и цветом:**
- Категория — уже плитка с иконкой (`CashflowCategoryIconView`) и акцентным цветом kind (`gradientColors`/`accentColor` из `CashflowCategoryTransactionSheetKind`) — переиспользуем, не переизобретаем стиль плитки, только адаптируем под cap-сетку (§2.2).

## 3. Риски и edge cases

- **R1 — Расхождение Dashboard FAB vs Cashflow-таб.** После фазы 3 (объединение шитов) Cashflow-таб получит новый 3-сегментный контейнер, а Dashboard FAB (`RootTabView.swift`) продолжит открывать 3 независимых старых шита (`CashflowIncomeTransactionSheet`/`CashflowExpenseTransactionSheet`/`CashflowTransferTransactionSheet`), которые физически рендерят ту же форму, но без сегмент-переключателя. Это создаст видимую пользователю непоследовательность (в одном месте свайп между Доход/Расход/Перевод, в другом — нет). Формально вне скоупа задачи ("таб Cashflow"), но нужно явное решение владельца: (а) оставить расхождение осознанно (Dashboard FAB — это "быстрый доступ", намеренно проще), либо (б) в отдельном фолоу-апе подключить тот же контейнер и к Dashboard FAB. **Рекомендация: (а) на этой итерации**, но зафиксировать как известный follow-up.
- **R2 — Recurring transactions (`recurrenceRule`).** Поле живёт только в полном `CashflowTransactionEditorView`, quick-tile flow туда просто перенаправляет (`navigationDestination`). Ни объединение шитов, ни cap категорий, ни вынос бюджета не трогают этот путь — recurrence остаётся доступной ровно как сейчас. Единственное, что нужно перепроверить в фазе реализации — что "Расписание" (`CashflowScheduledTransactionsView`, доступ через `managementSection`) остаётся достижимым из каждого таба контейнера (Income/Expense точно есть, Transfer — нет и не должно быть, т.к. переводы не входят в recurring-каталог, сверить при кодировании).
- **R3 — Валюта/конвертация.** Форма Income/Expense использует `state.displayCurrency` и `cashflowCurrencyCodeLabel`; бюджет считается в `currency ?? state.displayCurrency`. Вынос бюджет-карточки наружу не меняет валютную логику — просто дергаем тот же метод раньше по времени. Риск: если пользователь меняет валюту отображения на главном экране Cashflow, а `BudgetHeroCard` не переcчитается — нужно подписать `@Published`-снапшот на смену `state.displayCurrency` (см. §2.3 рекомендацию про VM-level published state — она закрывает и этот риск, если сделана правильно: один источник truth, один recompute-trigger).
- **R4 — Существующие пользовательские состояния (drag-reorder, pin).** Cap-логика (§2.2) **не удаляет и не переупорядочивает** сохранённые `CashflowCategoryOrderPrefs`/`CashflowCategoryPinPrefs` — она только меняет, сколько элементов показывается по умолчанию. Пользователь, который уже настроил порядок, увидит тот же порядок, просто обрезанный сверху (или полностью, если "показать все" открыто). Нет миграции данных, нет потери состояния. Единственный тонкий момент: если у пользователя pinned 10+ категорий (больше "верхнего предела" 8) — нужно решить, обрезать ли pinned-список тоже, или показывать ВСЕ pinned даже если их >8 (нарушит "6-8 плиток"). Рекомендация: **жёсткий cap на 8** даже для pinned — иначе теряется весь смысл "компактной сетки" для гипотетического пользователя, который запинил половину каталога.
- **R5 — Разделение типов шитов в коде (Income vs Expense).** `CashflowCategoryTransactionSheetKind` (enum `.income`/`.expense`) используется повсеместно как источник цветов/заголовков/фильтров (`CashflowCategoryTransactionSheetKind.swift`) — это НЕ мешает объединению в один контейнер, т.к. контейнер и так рендерит `CashflowCategoryTransactionSheet(kind: .expense)` и `CashflowCategoryTransactionSheet(kind: .income)` как две независимые страницы `TabView`, а не как один shared view с условными полями. Никакого распутывания `kind` не требуется — это ключевой довод в пользу того, что архитектура уже правильная (Single Responsibility на уровне страницы, не пытается стать одной God-формой с if/else на тип).
- **R6 — Пустой store / первый запуск.** Новый пользователь: 0 транзакций, 0 pinned категорий, 0 `BudgetPlan`. Cap-логика (§2.2) явно предусматривает fallback на дефолтный порядок каталога (не крашится на пустом pinned-set). `BudgetHeroCard.emptyCard` уже обрабатывает `snapshot == nil`. Breakdown (§2.4) — `entries.isEmpty` уже обрабатывается существующим кодом (`showNoCardsHint`), топ-3 cap не ломает этот путь (пустой массив после `.prefix(3)` остаётся пустым массивом).
- **R7 — Оффлайн/CloudKit недоступен.** Всё, что меняется — чистый локальный SwiftData/UserDefaults функционал (pin prefs, order prefs, budget plan — все локальные). CloudKit участвует только в backup/restore, полностью вне скоупа этой задачи. Нет новых сетевых вызовов, нет новых точек отказа при офлайне.
- **R8 — Разный object model для "категория" во время поиска.** Если cap показывает top-8, а пользователь начинает печатать в `searchText` — нужно явно снять cap на время активного поиска (иначе искомая категория вне топ-8 не найдётся, это баг, не фича). Зафиксировано в §2.2 ("search автоматически снимает cap") — важно не забыть при кодировании фазы 2.

## 4. Фазы реализации (порядок минимизирует риск регрессии)

### Фаза 0 — Почини фундамент: авто-транзакции от вкладов/кредитов (§1.8)

**Статус: РЕАЛИЗОВАНО ЧАСТИЧНО (2026-07-05).** Вклады — [x] полностью. Кредиты — [ ] сознательно отложены (дизайн + причина ниже). Catch-up — [x]. Секция «Предстоящие» — [ ] не реализована, остаток.

**Почему первой, перед визуальным редизайном:** это баг в данных пользователя (пропущенный/невидимый доход или расход), а не вопрос UX-полировки.

#### Шаг 1 [x] — Верификация: какой путь создания вклада живёт в развитии сегодня

Подтверждено грепом на HEAD `develop` (258295d, после мержа `feature/accounts-core`): **единственный актуальный путь для НОВЫХ вкладов — `AccountsCore`** (`FinanceAddAccountView.createDepositAccountOnNewCore()` → `AccountsCoreService.createAccount(kind: .deposit)` → `DepositInterestScheduler.regenerateFutureInterestEvents`). Легаси `Investment(isDeposit:)` + `InvestmentViewModel.syncDepositIncome` остаётся жить только для СТАРЫХ вкладов, заведённых до миграции (ветка `editingInvestment != nil` в `FinanceAddAccountView`) — не тронут в этой фазе, регрессии нет. Аналогично кредиты: новые — только через `AccountsCore` (`.loan`/`.debt`, `LoanMeta`).

#### Шаг 2 [x] — Точка вызова `generateRecurringTransactionsIfNeeded()`

Подтверждено: `CashflowViewModel.loadTransactions()` → `scheduleRecurringGeneration()` → `CashflowScheduledService.scheduleRecurringGeneration()` → `generateRecurringTransactionsIfNeeded()`. `loadTransactions()` вызывается при инициализации VM и при каждой мутации транзакций — движок вызывается регулярно, это НЕ было причиной поломки.

#### Шаг 3 [x] — Решение и реализация (вклады)

**Развилка:** легаси-мост (`syncDepositIncome`) чинить бессмысленно — он недостижим для новых вкладов после мержа AccountsCore. Выбран вариант **(б) read-мост «AccountsCore interest-событие → видимая Cashflow-доходная запись»**.

**Выбранный дизайн — материализация в `CashflowTransaction`, а НЕ read-слой при рендере ленты.** Обоснование:
- Cashflow (лента/breakdown/месячные итоги/бюджет-прогресс/уведомления) целиком читает `CashflowTransaction` через `FetchDescriptor` в ДЕСЯТКАХ мест `CashflowViewModel`/`CashflowAnalyticsService`. Подмешивать виртуальные (не persisted) записи в каждое из этих мест — на порядок инвазивнее и рискованнее, чем один раз материализовать событие в реальную строку.
- Материализация переиспользует УЖЕ существующий, проверенный в проекте паттерн идемпотентного upsert (`CashflowScheduledService.generateRecurringTransactionsIfNeeded` — `existsInMonth`-проверка перед вставкой), а не изобретает новый механизм синхронизации состояния.
- Баланс НЕ задваивается: материализованная транзакция создаётся с `affectsCardBalance = false`, `cardID = nil` — баланс вклада уже полностью отражён в `AccountsCore` через сам `AccountEvent`; материализованная строка нужна ТОЛЬКО для видимости в Cashflow (доход/бюджет/история), не является source of truth баланса.
- SwiftData остаётся единственным источником истины (принцип offline-first не нарушен) — материализованная строка не кэш и не производный view-only объект, а обычная персистентная запись, участвующая в backup/restore на общих основаниях.

**Реализация:**
- Новый файл `millio/UI/Services/Cashflow/AccountsCoreDepositCashflowBridge.swift` — класс `AccountsCoreDepositCashflowBridge` (`@MainActor`).
  - `materializeDueInterestIncome()` — фетчит ВСЕ `AccountEvent`, фильтрует `type == .interest && date <= today && account?.kind == .deposit` (фильтрация в Swift, НЕ через compound `#Predicate` с traversal через relationship — см. врезку про баг ниже), для каждого ещё не материализованного (по `importReferenceKey == AccountEvent.sourceTransactionID`) создаёт `CashflowTransaction(transactionType: .income, incomeCategory: .interest, amount:, currency: account.currency, transactionDate: event.date, note: account.name, affectsCardBalance: false, importSourceRaw: "accountsCoreDepositInterest", importReferenceKey: event.sourceTransactionID)`.
  - `note = account.name` — это ДАННЫЕ ПОЛЬЗОВАТЕЛЯ (он сам назвал вклад при создании), не UI-строка приложения, поэтому localization-правило про raw RU-литералы не применимо (аналогично тому, как имена карт/счетов нигде не локализуются).
  - `importSourceRaw`/`importReferenceKey` — переиспользованы существующие generic-поля модели `CashflowTransaction` (уже используются bulk-import feature для ровно такого же паттерна дедупа), а не заведено новое поле схемы — ноль изменений SwiftData-схемы, ноль риска для backup/restore (оба поля уже сериализуются в `export()`).
  - `syncDepositInterestLedger()` — сначала `DepositInterestScheduler.extendActiveDepositHorizons(...)` (см. ниже), затем `materializeDueInterestIncome()`.
  - `scheduleSync(onDidMaterialize:)` — фоновый запуск с guard-флагом от повторного входа, по образцу `CashflowScheduledService.scheduleRecurringGeneration()`.
- `CashflowViewModel`: новое `lazy var accountsCoreDepositCashflowBridge`, вызов `scheduleAccountsCoreDepositInterestSync()` добавлен в `loadTransactions()` рядом с двумя существующими генераторами (`scheduleDueAutoApplyIfNeeded`/`scheduleRecurringGeneration`) — общий движок `CashflowScheduledService` НЕ изменён (только то, что в него подаётся на вход, как и требовал AC).

**Найденная и закрытая ДОПОЛНИТЕЛЬНАЯ проблема — «горизонт вклада истекает через год»:** `DepositInterestScheduler.regenerateFutureInterestEvents` вызывался ТОЛЬКО при создании/правке счёта. Бессрочный вклад (`termEnd == nil`) получал события лишь на первые 12 месяцев от даты создания и НИКОГДА больше, если пользователь не открывал экран правки. Через год начисления молча прекратились бы — тот же класс бага «доход невидим», просто отложенно на 12 месяцев. Это НЕ было в исходных шагах плана, но обнаружено в процессе реализации и решено в рамках той же сессии (риск признан низким/механически безопасным — используется уже существующий, уже протестированный генератор, только новая точка вызова):
- Новый метод `DepositInterestScheduler.extendActiveDepositHorizons(context:asOf:calendar:)` — для каждого активного (`archivedAt == nil`) вклада проверяет, не исчерпан ли горизонт (последнее сгенерированное interest-событие раньше `asOf`), и если да — резюмирует генерацию СТРОГО ОТ ТОЧКИ ПОСЛЕДНЕГО СУЩЕСТВУЮЩЕГО СОБЫТИЯ (а не от `asOf`/`today`). Это принципиально: `regenerateFutureInterestEvents` считает всё `≤ asOf` «уже случившимся» и молча пропускает такие периоды — если резюмировать от `asOf`, периоды, попавшие в разрыв между исчерпанным горизонтом и текущей датой (когда `asOf` шагнул вперёд больше, чем на один горизонт разом — ровно наш сценарий «год не открывали экран правки»), никогда не были бы сгенерированы. Обнаружено эмпирически через unit-тест (`syncExtendsHorizonForPerpetualDepositBeyondOriginalWindow`), не силлогизмом — до фикса тест падал именно на этой границе.
- Архивные (закрытые) счета исключены из продления горизонта — досрочно закрытому вкладу новые проценты не начисляются (отдельный тест `archivedDepositIsExcludedFromHorizonExtensionButPastDueEventsStillMaterialize`).
- Вызывается ОДИН РАЗ, только когда горизонт реально исчерпан (проверка `latestGeneratedDate < asOf` перед резюме) — НЕ на каждой загрузке таба Cashflow (это было бы дорого и не нужно): пока горизонт «здоровый» (последнее событие в будущем относительно сегодня), метод — no-op.

#### Шаг 4 [⏸️ ОТЛОЖЕНО] — Кредиты

**Решение: НЕ реализовывать в этой сессии, отдельный дизайн-цикл.** Причина — это не read-мост (как вклады), а фича с нуля в ДВУХ системах одновременно:
1. На стороне `AccountsCore` для кредитов (`.loan`/`.debt`, `LoanMeta`) **нет вообще никакого аналога `DepositInterestScheduler`** — ни планировщика платежей, ни авто-амортизации, ни расчёта разбивки платежа на проценты/тело долга. Расчёт ежемесячного платежа в `AccountDetailView` — чисто отображательный (аннуитетная формула для UI-строки), не генерирует события.
2. Легаси `Credit`/`CreditManager` ИМЕЕТ авто-амортизацию (`remainingAmountAdjustment` при каждом `loadCredits`), но БЕЗ создания транзакций — значит recurring-механизм для легаси-кредитов должен согласовываться с уже существующим пересчётом остатка, чтобы не задвоить погашение (риск из §1.8.C, подтверждён).
3. Итоговый объём работы: (а) LoanPaymentScheduler-аналог `DepositInterestScheduler` для новых кредитов — генерация графика платежей с разбивкой проценты/тело долга (амортизационная таблица, а не простое умножение как у вклада); (б) Cashflow-мост по аналогии с `AccountsCoreDepositCashflowBridge`; (в) согласование с легаси авто-амортизацией. Это сопоставимо по объёму с целой фазой `accounts-core-rebuild-plan` (Фаза 3, которая делала именно это для вкладов), а не с «починкой моста» — трудозатратнее и рискованнее вкладов, как и предсказывал §1.8.C.
4. **Рекомендация:** отдельный план (`plans/YYYY-MM-DD__credit-payment-scheduler.md`), отдельная stress-test-сессия перед кодированием (правило 7 workspace — транзакции в данные пользователя задним числом), отдельное решение владельца по приоритету.

#### Шаг 5 [x] — Catch-up (пропущенные даты)

Материализация «одним проходом» естественно закрывает catch-up: `materializeDueInterestIncome()` фетчит ВСЕ due-события разом (не по одному), поэтому если приложение не открывали несколько месяцев — все пропущенные периоды материализуются за один вызов с их исторически верными датами (даты события, не «сегодня»). Подтверждено тестом `catchUpMaterializesAllMissedPeriodsWithHistoricalDatesAtOnce` (4 месяца пропуска → 4 корректно датированные транзакции одним вызовом, идемпотентно при повторном вызове).

#### Шаг 6 [⏸️ НЕ РЕАЛИЗОВАНО] — Секция «Предстоящие» на главном экране Cashflow

Не реализовано в этой сессии — весь бюджет времени ушёл на вклады (мост + найденный баг горизонта + тесты) и решение по кредитам. Остаётся открытым пунктом для Фазы 0 либо для отдельной итерации перед Фазой 3 (переиспользовать вычисления `CashflowScheduledTransactionsView`, не считать заново).

**Acceptance criteria — покрытие:**
- ✅ Вклад с датой выплаты процентов X → в дату X (не раньше, не позже) в Cashflow появляется доходная транзакция на верную сумму, привязанная к вкладу (через `note = account.name`, `importReferenceKey` кодирует `accountID`). Тест: `dueInterestEventMaterializesAsVisibleIncomeTransaction`.
- ⏸️ Кредит с датой платежа Y → отложено, см. Шаг 4.

- ⏸️ Секция «Предстоящие» — не реализована (Шаг 6).
- ✅ Регрессия: общий движок `CashflowScheduledService` не изменён — только новый независимый вызов добавлен в `loadTransactions()` рядом с существующими. ### 7.2 Ключевые факты из верификации (влияют на реализацию)

- **Валютная дыра quick-entry подтверждена** дословно: `currency: viewModel.state.displayCurrency` (`CashflowQuickEntrySheet.swift:296`), выбор счёта есть, валюта к счёту не привязана. Downstream не чинит: `CashflowPersistenceService` сохраняет `transaction.currency` как есть.
- **BudgetHeroCard — подтверждённый мёртвый код**, безопасно подключать. Нюанс: `monthlyBudgetSummary` дефолтит валюту из `state.displayCurrency` и может выставлять `currencyConversionWarning` — recompute-подписка на смену `displayCurrency` обязательна (R3).
- **Движок recurring исправен**: catch-up историческими датами подтверждён, дедуп по дню (weekly НЕ ломается — проверка `isDate(inSameDayAs:)`, не по месяцу), точки вызова живые. Две оговорки для Фазы 0: (а) скан ограничен 366×6 итераций от `templateDate` — weekly-серии старше ~6 лет перестанут догенерироваться; (б) **tombstone нет** — удалённый пользователем сгенерированный экземпляр ВОСКРЕСНЕТ при следующем запуске. Для авто-платежей вкладов/кредитов (б) критичен — материализация вкладов из Фазы 0 наследует ЭТУ ЖЕ особенность (см. секцию Фазы 0, «известный унаследованный edge case»), не решается в этой сессии.
- **Типографика суммы**: использовать существующие токены `Font.millioDisplayLarge` (52pt semibold) / `millioDisplay` (30pt bold) из `AppTypography.swift`; для стабильной ширины цифр при `.numericText()`-анимации — `.monospacedDigit()` модификатором.
- **Breakdown уже отсортирован** по убыванию суммы на уровне сервиса (`CashflowAnalyticsService.swift:225-230`) — топ-3 = простой `prefix(3)`.
- **Ловушка SwiftData #Predicate + relationship traversal (найдено в Фазе 0, важно для будущих фаз):** compound-предикат вида `#Predicate<AccountEvent> { $0.typeRaw == X && $0.date <= Y && $0.account?.kindRaw == Z }` (traversal через optional-relationship В СОЧЕТАНИИ с датой) эмпирически возвращал 0 результатов при заведомо существующих совпадениях (обнаружено через падающие тесты моста вкладов). Одиночные traversal-условия (`$0.account?.id == accountID`) работают нормально (уже используются в `DepositInterestScheduler`) — проблема именно в СОЧЕТАНИИ traversal + сравнения дат в одном предикате. Рабочее решение — широкий `FetchDescriptor` без предиката + фильтрация в Swift (`.filter { }`), тот же приём, что уже использует `CashflowScheduledService`/`CashflowScheduledService.applyDuePlannedTransactionsIfNeeded` (fetch всех транзакций → фильтрация в памяти). **Рекомендация для Фазы 3 и далее: избегать compound `#Predicate` с relationship-traversal, предпочитать широкий fetch + `.filter` в Swift** — дешевле по риску, чем тратить время на диагностику непредсказуемого поведения макроса.

### 7.3 Правки плана по аудиту полноты (обязательны к учёту в фазах)

1. **[HIGH] Backfill существующих продуктов — новый шаг Фазы 0.** ✅ ЗАКРЫТО для вкладов: материализация (`materializeDueInterestIncome`) не различает «старый»/«новый» вклад — она читает уже существующие `AccountEvent(.interest)` независимо от того, когда счёт был создан, поэтому вклады, заведённые ДО фикса, тоже получают видимый доход при следующей загрузке Cashflow (никакой отдельной миграции не потребовалось — это естественное свойство read-моста, а не backfill-скрипта).
2. **Жизненный цикл продукта — новый шаг Фазы 0**: (а) редактирование вклада (ставка/сумма/срок) → `DepositInterestScheduler.regenerateFutureInterestEvents` уже вызывается при правке (существующий код, не Фаза 0) и корректно пересчитывает БУДУЩИЕ события, не трогая прошлые/уже материализованные — совместимо с мостом без дополнительных изменений; (б) закрытие вклада (`archivedAt`) → `extendActiveDepositHorizons` больше не продлевает горизонт для архивных счетов (реализовано и протестировано), но уже сгенерированные ДО закрытия due-события по-прежнему материализуются (осознанно — это исторически заработанный доход, не «доход после закрытия»); (в) кредиты (переменные суммы, дифференцированный платёж) — отложены целиком (Фаза 0, Шаг 4), пункт не применим в этой сессии.
