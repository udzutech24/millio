## Цель (формулировка владельца)

Для отображения денег — ЕДИНЫЙ, максимально простой источник истины: числа на экране
никогда не расходятся и не ломаются при мутациях (удаление счетов, фильтры, группы).

## Что подтверждено аудитом (по коду develop, 2026-07-18)

1. **CONFIRMED** — удаление счёта переписывает историю. `Account.snapshots` имеет
   `deleteRule: .cascade` (`millio/Core/AccountsCore/Account.swift:36`) → исторические
   `AccountDailySnapshot` удаляются каскадом. `AccountsTotalsService.totalAt/seriesBetween`
   (`.../AccountsTotalsService.swift:39-88`) суммируют только ныне существующие счета
   (`participates(on:)`), без учёта «был жив на дату X».
2. **CONFIRMED** — на «Динамике» ТРИ параллельных вычисления итога: заголовок-дельта
   (`FinanceDynamicsViewModel.swift`, вклад ядра `:839-868` + `calculateDeltaPercent`),
   график (`buildTimeSeriesData` + `addingCoreContribution`), карточка «Общая сумма»
   (`FinanceDynamicsPresentation.totalRow:12-39`). Комментарии в коде сами признают «три пути».
3. **PLAUSIBLE** — база периода клэмпится по-разному для заголовка и графика
   (`resolvedPeriodDates` vs `getAccountsForCalculation(scope:.historicalInterval)`) →
   расхождения «+7099.6%» vs «+146.8%»; счёт, созданный внутри периода, выглядит как рост из ничего.
4. **PLAUSIBLE** — дубль даты «18.07» на оси 1D: `eventDates` из `createdAt/updatedAt`
   без дедупликации по календарному дню.
5. **CONFIRMED (пока безопасно)** — тотал «Счета» (`FinanceTotalsService`) и Активы/Обязательства
   (`FinanceViewModel.calculateGroupTotal` + `FinanceAccountsSectionSplitter`) — два независимых
   расчёта без инварианта; хвост — дубль секции «Без группы».

## Целевая архитектура (гипотеза — проверить и уточнить на Ф1)

Один продюсер строит для периода кортеж **`(periodStart, periodEnd, [точки])`**. Заголовок-дельта,
карточка «Общая сумма» и график — ПРОИЗВОДНЫЕ этого же массива:
- заголовок дельта = `последняя.точка − первая.точка`;
- карточка `totalRow` = те же endpoints;
- график = сам массив.

**Ponytail-лестница (обязательна на Ф1 перед проектированием):** сначала проверить, можно ли
сделать продюсером УЖЕ существующий `AccountsTotalsService.seriesBetween` (одна точка на день,
курс своей даты) + per-account агрегацию «Групп» из 6b — вместо нового слоя. Легаси-мир пока
не портирован на ядро → минимальный вариант: единый per-day series-builder, который складывает
легаси-реплей и core-вклад ОДИН РАЗ на день, а заголовок/карточка читают его концы. Новых
сущностей не плодить; удалить дублирующие пути `totalAt`/`totalRow`-recompute, а не добавить четвёртый.

### Фаза 2 — Единый продюсер серии `(periodStart, periodEnd, [точки])`
- Один метод строит массив точек периода (переиспользуя `seriesBetween`/per-account агрегацию, не новый слой).
- Дедуп `eventDates` по календарному дню (закрывает находку 4); единый `resolvedPeriodDates`
  для заголовка И графика (закрывает находку 3).
- **Решение владельца (Q2):** база периода = **0** для счётов, созданных после начала периода
  (первая точка счёта = его `createdAt`). Клэмпа к дате создания нет; дельта честно показывает
  появившиеся на счёт деньги.
- Легаси-вклад и core-вклад складываются ОДИН раз на день внутри продюсера.

### Фаза 3 — Заголовок и карточка ДЕРИВАТ от массива
- Заголовок-дельта = `последняя − первая` точки серии; карточка `totalRow` = те же endpoints.
- Удалить параллельные recompute-пути `totalAt`-в-заголовке и `totalRow`-над-breakdown
  (боль ≠ красота: убираем реальные источники расхождения, а не «на всякий»).

### Фаза 4 — Инвариант тестом
- Тест: **«заголовок == (последняя−первая точка серии) == сумма карточки»** для ВСЕХ периодов
  (1D/1W/1M/1Y/All), включая фильтры групп/счетов и single-account.
- Тест дедупликации оси (нет двух точек одного календарного дня).
- **Решение владельца (Q3):** тест включает archived-счета в базу и историю (архивация не меняет прошлое).
- Регрессионный тест (Q1): удаление счёта (soft-delete) не смещает исторические точки чужих счетов.

### Фаза 5 — Семантика удаления истории (soft-delete/tombstone) — [x] РЕАЛИЗОВАН
**Решение владельца (Q1)**: История сохраняется через soft-delete/tombstone.
**Выбранный механизм (отклонение от буквы плана, ponytail):** tombstone на РОДИТЕЛЕ `Account.deletedAt: Date?`,
а НЕ на `AccountDailySnapshot`. Причина: переиспользует уже протестированный `participates(on:)`
(та же жёсткая отсечка, что `archivedAt`) как единый чок-поинт → главные списки/тоталы фильтруют
автоматически; сохраняет currency/meta/events/snapshots для корректного исторического реплея и
конвертации по курсу даты; каскад `.cascade` на snapshots НЕ трогаем (нет orphan'ов, нет дубляжа
currency на снапшот, per-account группировка цела). Вариант «tombstone на снапшоте + nullify»
отклонён: терял бы currency/meta и требовал нового пути суммирования orphan'ов + не выражал «вклад
после удаления = 0» без ещё одного поля.
- `Account.deletedAt: Date?` + `participates(on:)` = `date < min(archivedAt, deletedAt)`.
- `AccountsCoreService.softDelete(_:on:)` (tombstone) для юзерского удаления; `physicallyDelete` (hard
  cascade) ОСТАВЛЕН для дедуп-двойников `LegacyAccountConverter` (истории для сохранения нет).
- UI-репойнт: `ArchivedAccountsView` + `FinanceViewModel.deleteAccountPermanently` → `softDelete`;
  списки архива (`ArchivedAccountsView`, `hasArchivedNewCoreAccounts`) фильтруют `deletedAt == nil`.
- Round-trip `deletedAt`: `Account.export`/`AccountImporter` (backup) + reconciliation DTO
  (`ScopeMergeReader`/`Dedup`/`Snapshot`) — иначе tombstone воскресал бы при guest→user merge.
- **Миграция:** БЕЗ бампа версии схемы. Новая версия для optional-атрибута НЕВОЗМОЖНА (V6.models
  ссылался бы на тот же тип Account → идентичная схема V5==V6 → краш ModelContainer до bootstrap,
  проверено на прогоне). Optional-поле = каноничная АВТО-lightweight-миграция SwiftData (nil у старых
  строк), Находка-2 (про таблицу, не колонку) не наступает, CloudKit-совместимо (как archivedAt).
- Тесты: `AccountSoftDeleteTests` (7): participates-отсечка, прошлое неизменно, вклад после = 0,
  today/архив-список исключают, backup round-trip. Гейт 9 классов **82/82 ×2 зелёные**.

### Фаза 7 — Кредитные карты: долг вместо остатка в общем тотале
**Статус:** не начата. **Реализация:** ПОСЛЕ мержа Ф0–Ф6 в develop.

- **Связанный известный долг:** тесно привязан к сломанному UI-тоггку `credit.includeInTotal` — `normalizeCreditsIncludeInTotal` сбрасывает его в true (найдено при unified-totals 2026-07-05, не чинено). Проверить связь при research.
- **Скоуп research:** семантика кредит-счетов в `AccountTotalPolicy` / `AccountsTotalsService` (знак вклада в тоталы: долг = отрицательный), красная маркировка в UI секций «Обязательства» (Liabilities), связь с продюсером серии Ф2 (где кредит участвует в график-точках с правильным знаком), инвариант-тесты Ф4 на знак.
- **Acceptance criteria:**
  - Кредитная карта в общем тотале участвует со знаком долга (уменьшает сальдо, как Ф5 для архивных).
  - UI: секция «Обязательства» красная, как обязательство, не как актив.
  - Инвариант-тесты Ф4 (заголовок == график == карточка) остаются зелёными.
