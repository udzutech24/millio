# Research / Design: фундаментальная перестройка ядра счетов Millio

**Дата:** 2026-07-04
**Режим:** L (архитектура). Research → Spec → Plan → Build.
**Решение владельца:** чинить основательно (приложение не двигается на костылях), **без миграции старых данных** (данные пересобираются), **начать с типов счетов**.
**Вход:** аудит `plans/2026-07-02__accounts-system-audit.md` (R1–R4, P1–P5, S1–S5, C1–C4) + логи с устройства 2026-07-04 (BUG#3 requireEveryClosedDay доказан).

---

## Корневой диагноз одной фразой
Баланс счёта имеет **двух хозяев**: хранимое поле (`card.balance`, `investment.amount`, `credit.remainingAmount`) И реплей транзакций. Три экрана считают «одно число» тремя путями. Снапшоты, тоталы, график — производные, которые расходятся, потому что нет единого источника истины. Плюс модель кривая: 3 разнородных сущности + строковая связь `FinanceAccount`, вклад воткнут в `Investment`, снапшот без `@Relationship`.

Раз без миграции — можно спроектировать чисто, а не латать.

---

## Принцип перестройки: event-sourcing (единый источник истины)

**Всё, что меняет баланс/количество/стоимость — это событие.** Баланс не хранится как «правда», а выводится реплеем событий до нужной даты. Тогда снапшот, тотал и график — тривиальные производные одной функции `balanceAt(account, date)`, и расходиться физически не могут.

| Тип счёта | Что такое «событие» | balanceAt(date) |
|---|---|---|
| Наличка / дебет / банковский счёт | приход/расход (transaction) | initial + Σ tx ≤ date |
| Кредитная карта | трата/погашение (transaction) | limit − долг(Σ tx) |
| Вклад / депозит | пополнение/снятие + начисление % (scheduled tx) | Σ tx ≤ date |
| Кредит / займ | выдача + платежи (transaction) | −(остаток по Σ tx) |
| Инвестиция рыночная (акции/крипта/облиг/металл) | купля/продажа (изменение количества) | quantity(Σ tx) × price(date) |
| Актив нерыночный (недвижимость/бизнес/авто) | переоценка (revaluation event) | последняя переоценка ≤ date |
| Долг (мне / я должен) | возникновение + погашение | Σ tx ≤ date |

«Прямое редактирование баланса» в UI сохраняется как удобство, но под капотом порождает **корректирующее событие** (adjustment tx), а не пишет в поле напрямую. Хранимый баланс остаётся только как **кэш** для скорости, пересчитываемый из событий.

**Что это чинит разом:**
- R1 (три пути) → один путь `balanceAt`. Accounts, Analytics, график — одна функция.
- R3/BUG#3 (пустой график) → снапшот больше не «обязателен каждый день»; `balanceAt` всегда определён реплеем, дырок не бывает by design. Forward-fill не нужен — он становится свойством модели.
- R4 (плывущие курсы) → курс фиксируется в событии/на дате, исторический реплей детерминирован.
- P1–P5 (архив/удаление) → чистая семантика: удаление = удаление событий (каскад через `@Relationship`), архив = флаг «не показывать/не считать», единый предикат.
- Наличка/вклад/иностранный счёт → явные типы, а не «Card в костыле» и «депозит внутри Investment».

## Новая модель (черновик, начинаем с типов — как просил владелец)

```
Account (единая сущность, @Model)
  id, name, kind: AccountKind, currency, createdAt, archivedAt?, includeInTotal, group?
  // kind-specific через опциональные поля или дочерние value-типы:
  creditLimit?          (для .creditCard)
  depositTerms?         (ставка, капитализация, срок — для .deposit)
  marketSymbol?         (тикер — для .marketInvestment)
  @Relationship(deleteRule: .cascade) transactions: [AccountEvent]
  @Relationship(deleteRule: .cascade) snapshots: [AccountDailySnapshot]   // теперь настоящая связь

enum AccountKind: cash, debitAccount, creditCard, deposit, loan,
                  marketInvestment, manualAsset, debt

AccountEvent (@Model) — событие изменения
  date, kind: (income|expense|buy|sell|revaluation|interest|adjustment),
  amount|quantity, unitPrice?, fxRateAtDate?, note

Group (@Model) — только ярлык-контейнер
  name, colorHex, displayCurrency, @Relationship(.nullify) accounts
```

Снапшот становится **производным кэшем** (для скорости графика на больших историях), а не источником — его можно в любой момент выкинуть и пересобрать реплеем. Отсюда «без миграции»: старые снапшоты просто удаляем, пересобираем из событий.

## Открытые вопросы к владельцу (форки перед спекой)
1. **Таксономия типов** — согласовать список `AccountKind` (8 типов выше). Убрать/добавить?
2. **Event-sourcing vs stored-balance** — согласен на event-sourcing как единый источник (рекомендация), или оставить хранимый баланс главным, а транзакции — вторичными?
3. **Вклад** — вынести в отдельный тип `.deposit` с процентами/капитализацией (рекомендация), или оставить как инвестицию?
4. **Объём первого куска** — весь rebuild сразу (L, недели) или вертикальный срез: сначала наличка+дебет+кредит на новом ядре, потом инвестиции/вклады?

## Предлагаемый порядок (Bulletproof L)
1. **Spec** нового ядра (модель + `balanceAt` контракт + семантика архив/удаление) — после согласования форков.
2. **Plan** с фазами (вертикальными срезами по типам).
3. **Build** пофазно: (a) модель+события+`balanceAt` для денежных типов → (b) снапшот-кэш как производная → (c) единый тотал → (d) инвестиции/рыночная цена → (e) вклады+проценты → (f) архив/удаление/группы → (g) чистка/пересборка.
4. Каждая фаза: /stress-test + тесты + self-audit. Старую снапшот-ветку `feature/dynamics-chart-fix` держим как fallback.
