# 15 промтов методологии

Авторские промты Артемия Миллера (вайб-практикум, март 2026) + Code Review, Security Scan, Continuous Improvement. Копируй целиком, адаптируй под задачу, вставляй в Claude Code.

**Список:**
1. Code to solve problems, not code for code's sake
2. Deep Research → Best Solution
3. Challenge Loop — 3 вопроса перед финализацией
4. Think Several Steps Ahead
5. Self-Audit после каждой фазы
6. Prove the Bug is Real
7. Impact Analysis — «Мы что-то сломали?»
8. Anti-Rationalization Stop Hook
9. Progressive Disclosure + 40% Rule
10. Guard Phrase to Start Coding
11. Annotation Cycle
12. Recommend, Don't Just Ask
13. Code Review (перед мержем)
14. Security Scan
15. Continuous Improvement — рост команды через наблюдение

## 01. Code to solve problems, not code for code's sake

**Когда:** в начале любой задачи, первым сообщением.

```
Перед любым изменением кода ответь себе на 2 вопроса:

1. Это изменение реально решает поставленную задачу?
2. Это самое эффективное из известных решений?

Если на любой ответ «нет» или «не уверен» — остановись.
Не пиши код. Сначала: исследуй альтернативы, выбери лучшую, объясни почему.

Запрещено:
- Менять то, что не относится к задаче (drive-by рефакторинг)
- Добавлять «на всякий случай» (валидации, обёртки, абстракции под гипотетику)
- Делать «красивее» без влияния на корректность
- Брать первое пришедшее в голову решение, не сравнив с альтернативами

Правило: каждая строка нового/изменённого кода должна напрямую закрывать
требование задачи. Не можешь связать строку с требованием — удали её.
```

## 02. Deep Research → Best Solution

**Когда:** в начале большой задачи, до спеки и плана.

```
Режим: только чтение. Никакого кода.

Задача исследования: {опиши задачу}

Действия:
1. Запусти параллельно несколько под-агентов на исследование структуры кодбазы (по одному на область: модели/архитектура, существующие паттерны, зависимости, тесты).
2. WebSearch: кто уже решил эту проблему? Какой подход выбрали? Какое решение считается best practice сегодня?
3. Собери все находки в один артефакт.

Артефакт исследования ОБЯЗАН заканчиваться разделом «Рекомендация»:
- Какое решение выбрано как лучшее.
- Почему именно оно (сравнение с 2-3 альтернативами).
- Что нужно учесть при имплементации.

Не вываливай на меня список опций без вывода. Без рекомендации — артефакт неполный.

Сохрани в thoughts/research/YYYY-MM-DD-<task>.md.
```

## 03. Challenge Loop — 3 вопроса перед финализацией плана

**Когда:** после того как агент написал план, ДО кодинга.

```
Перед тем как финализировать план, ответь на 3 вопроса:

1. РЕШАЕТ ЛИ ЭТО ПРОБЛЕМУ?
   Сопоставь каждый пункт плана с acceptance criteria из спеки.
   Если хоть один критерий не покрыт — план неполный.

2. ЭТО САМОЕ ЭФФЕКТИВНОЕ РЕШЕНИЕ?
   Найди: кто уже решал эту проблему? Какой подход выбрали?
   Назови 2-3 альтернативных подхода (включая найденные через research).
   Для каждого: плюсы, минусы, трудоёмкость.
   Обоснуй, почему выбранный подход лучше всех альтернатив.

3. ЕСТЬ ЛИ В ПЛАНЕ «КОД РАДИ КОДА»?
   Каждое изменение должно напрямую обслуживать acceptance criteria.
   Если изменение не привязано к задаче — удали.
   Drive-by рефакторинг — отдельная задача, не часть этой.

Только после прохождения всех 3 вопросов план можно считать готовым.
Запиши Challenge Log в сам план.
```

## 04. Think Several Steps Ahead

**Когда:** на стадии планирования, до кода.

```
До того как написать строчку кода, продумай ВСЕ возможные проблемы заранее.

Задай себе вопросы:
- Что сломается через неделю? Через месяц?
- Что произойдёт под нагрузкой в 100x?
- Что будет, если данных ноль? Если данных миллион?
- Что если пользователь сделает то, чего я не ожидаю?
- Что с конкурентными запросами / гонками?
- Что с откатами / повторами / частичными сбоями?
- Какие edge cases у входных данных (null, пустота, странные символы, очень длинные значения)?
- Что с обратной совместимостью?

Реши проблемы ДО того, как они появились.
Не «исправлю потом» — «не допущу сейчас».

Список найденных edge cases вынеси отдельной секцией в план.
```

## 05. Self-Audit после каждой фазы

**Когда:** сразу после завершения куска реализации, до «готово».

```
Аудит реализации текущей фазы. Свежими глазами.

1. SPEC COMPLIANCE
   Открой спеку. Пройдись по каждому acceptance criterion.
   Для каждого: реализован? Где именно в коде (файл:строка)?
   Если хоть один не покрыт — закончи его сейчас, не оставляй на «потом».

2. CHALLENGE THE SOLUTION
   Посмотри на написанный код свежими глазами.
   - Это правда решает задачу из спеки?
   - Есть ли способ проще / эффективнее?
   - Есть ли «код ради кода» — изменения, не связанные с задачей? Удали их.

Только после этого можешь сказать «фаза завершена».
Запрещено говорить «готово», если хоть один criterion не покрыт.
```

## 06. Prove the Bug is Real (анти-галлюцинация)

**Когда:** когда агент начинает «находить и исправлять баги», которые не просили.

```
Для КАЖДОГО найденного бага ответь:

1. Это РЕАЛЬНЫЙ баг или false positive?
2. Можешь ли ты доказать, что баг воспроизводится? Опиши конкретный сценарий: вход → ожидание → реальное поведение.
3. Если не можешь доказать — это НЕ баг. Не трогай код.

ПРАВИЛО: не исправляй код «для красоты» или «на всякий случай».
Исправляй ТОЛЬКО доказанные баги, которые реально влияют на функциональность.

Каждый «фикс» без доказательства = риск ввести новый баг.

Если сомневаешься между «исправить» и «оставить» — оставь.
```

## 07. Impact Analysis — «Мы что-то сломали?»

**Когда:** перед мержем любой ветки, после изменений интерфейсов/API/типов.

```
ОБЯЗАТЕЛЬНАЯ ПРОВЕРКА ПЕРЕД МЕРЖЕМ:

1. РЕГРЕССИЯ
   Какие модули/функции зависят от изменённых файлов?
   Запусти ВСЕ тесты проекта (не только текущей фазы).
   Если что-то сломалось — это приоритет №1.

2. SIDE EFFECTS
   Изменились ли какие-то контракты/интерфейсы (API, props, типы, схема БД)?
   Если да — кто их использует? Все ли потребители обновлены?

3. THINK AHEAD
   Какие проблемы эти изменения могут вызвать через неделю/месяц?
   Edge cases, которые мы не протестировали?
   Что произойдёт с: нулевыми данными? Огромными данными? Конкурентными запросами?
   Что если пользователь сделает что-то неожиданное?

4. COMPATIBILITY
   Сохранена ли обратная совместимость?
   Нужны ли миграции данных?
   Нужен ли feature flag для постепенной раскатки?

Без прохождения всех 4 пунктов — не мержим.
```

## 08. Anti-Rationalization Stop Hook

**Когда:** как автоматический Stop hook в `.claude/settings.json` или ручно когда агент говорит «готово».

```
Ты — JSON-only evaluator. Отвечай ТОЛЬКО raw JSON, без markdown.

Проверь финальный ответ ассистента. Отклони, если:
- Рационализирует незавершённую работу: «pre-existing», «out of scope», «follow-up», «not blocking»
- Перечисляет проблемы, не починив их
- Пропускает падающие тесты / lint с отмазками
- Делает изменения, не связанные с поставленной задачей («код ради кода»)
- Заявляет о завершении, не запустив verification gates (typecheck, lint, tests)

Ответ:
{"ok": false, "reason": "[конкретная проблема]. Вернись и доделай."}
или:
{"ok": true}
```

## 09. Progressive Disclosure + 40% Rule

**Когда:** в начале большой задачи — установочные правила на сессию.

```
Правила управления контекстом на эту сессию:

1. ПРАВИЛО 40%
   Держи контекст в диапазоне 40-60% окна.
   В районе 50% делай ручной /compact — не жди автокомпакта.
   Если контекст перегружен — сохрани прогресс в handoff-файл, /clear, начни заново.

2. PROGRESSIVE DISCLOSURE
   Не вываливай в контекст всю кодбазу.
   - Research: подключай sub-агентов, бери от них компактные саммари.
   - Planning: только саммари + ключевые интерфейсы, не полные файлы.
   - Implementation: только файлы текущей фазы.
   - В CLAUDE.md ссылайся на пути к докам, а не @-импортируй файлы.

3. FRESH CONTEXT МЕЖДУ СТАДИЯМИ
   Каждая большая стадия = чистое окно.
   Перед /clear создай handoff-файл с прогрессом и контекстом для следующей стадии.

Эти правила важнее скорости. Лучше /clear лишний раз, чем работать в Dumb Zone.
```

## 10. Guard Phrase to Start Coding

**Когда:** в начале сессии, как часть установочных правил.

```
Правило старта реализации.

Тебе ЗАПРЕЩЕНО писать или менять код до тех пор, пока:
1. План финализирован.
2. Все мои аннотации / NOTE-комментарии в плане отработаны.
3. Я явно сказал триггер-фразу: «Implement Phase N according to plan» (или «Реализуй фазу N по плану»).

До этого момента ты можешь:
- Читать файлы.
- Запускать research-агентов.
- Уточнять план.
- Задавать вопросы.

Но НЕ редактировать код. Никаких «давай я уже начну, а потом обсудим».

Если я случайно дам тебе двусмысленную команду — переспроси, не начинай кодить по своей интерпретации.
```

## 11. Annotation Cycle — совместное редактирование плана

**Когда:** когда агент сделал первый драфт плана/спеки, а у тебя есть правки.

```
Workflow совместного редактирования плана:

1. Ты драфтишь план / спеку / документ в файл.
2. Я открываю файл в редакторе и добавляю комментарии в формате:

   > NOTE: тут не учёл случай X, переделай
   > NOTE: эту фазу разнеси на 2 — слишком большая
   > NOTE: вместо подхода А используй Б, потому что...

3. Я говорю тебе: «Address all notes, don't implement yet» (или «Отработай все NOTE, не реализуй»).
4. Ты проходишься по каждому NOTE, изменяешь план, удаляешь NOTE после отработки.
5. Возвращаешь обновлённый план.
6. Повторяем, пока в файле не останется ни одного NOTE.

Только после этого план считается финализированным и готовым к реализации.
```

## 12. Recommend, Don't Just Ask

**Когда:** базовое правило — постоянно.

```
Правило задавания вопросов мне:

Когда тебе нужно решение от меня — не вываливай голый вопрос.
Сначала сам проанализируй варианты, потом задай вопрос с рекомендацией.

Формат вопроса:

«Развилка: А или Б.
- А: плюсы / минусы / стоимость
- Б: плюсы / минусы / стоимость
- Моя рекомендация: А, потому что [причина]
- Подтверди или возрази.»

НЕ задавай вопросы без рекомендации.
НЕ задавай очевидные вопросы (если ответ ясен из контекста — выбирай сам).
НЕ задавай по 5 вопросов подряд — сгруппируй в один связный.

Если развилка реально 50/50 и ты не можешь рекомендовать — так и скажи: «Не могу рекомендовать, оба варианта равноценны, выбирай ты».
```

## 13. Code Review (перед мержем)

**Когда:** после self-audit и impact analysis, перед созданием PR / мержем в main.

```
Режим: строгое code review. Ты не автор кода, ты reviewer. Будь придирчив.

Проверь diff по слоям:

1. SPEC ALIGNMENT
   - Каждый acceptance criterion из spec — покрыт? Где именно?
   - Есть ли изменения ВНЕ scope спеки? Если да — вынеси в отдельную задачу.

2. CODE QUALITY
   - Дубли логики? Магические константы? Непонятные имена?
   - Есть ли «код ради кода» — абстракции / обёртки / валидации без причины? Удалить.
   - Есть ли error handling там, где ошибка невозможна? Убрать.
   - Нет ли комментариев, описывающих WHAT вместо WHY? Убрать.

3. CORRECTNESS
   - Edge cases: null / пустота / огромные данные / конкурентность / откаты.
   - Race conditions, неатомарные операции, частичные сбои.
   - Обратная совместимость — не сломали ли контракты?

4. TESTS
   - Покрыты ли acceptance criteria тестами?
   - Тесты проверяют поведение, а не реализацию?
   - Есть ли хрупкие тесты (зависят от порядка, времени, внешних сервисов)?

5. PERFORMANCE (если релевантно)
   - N+1 запросы? Тяжёлые операции в цикле? Лишние рендеры?
   - Что будет при 100x нагрузке?

6. REGRESSIONS
   - Запусти все тесты проекта (не только новые).
   - Все green? Если нет — это блокер.

Вывод: список замечаний с приоритетом [BLOCKER / MAJOR / MINOR / NITPICK].
Если BLOCKER или MAJOR — не мержим, возвращаем в работу.
```

## 14. Security Scan

**Когда:** перед мержем фичи, которая трогает аутентификацию / данные пользователя / внешние API / загрузку файлов / SQL-запросы.

```
Security scan по OWASP Top 10 + common sense. Ищи уязвимости, не уверенность.

1. INPUT VALIDATION
   - Все ли внешние входы валидируются? (form, query, body, headers, cookies, file uploads)
   - Есть ли SQL injection (прямая склейка строк в запрос)?
   - Есть ли XSS (unescaped вывод в HTML, dangerouslySetInnerHTML без санитайза)?
   - Есть ли command injection (exec/spawn с user input)?
   - Path traversal (file reads с user input в пути)?

2. AUTH & AUTHORIZATION
   - Каждый эндпоинт — проверяет auth?
   - Каждая операция — проверяет owner / permission?
   - IDOR: могу ли я подставить чужой id и получить/изменить чужие данные?
   - Секреты / ключи / токены — не утекают в логи, ответы, коммиты?

3. SECRETS
   - `.env` не в git?
   - Нет hardcoded токенов / паролей / API-ключей?
   - Секреты не светятся в error messages?

4. DATA EXPOSURE
   - API не возвращает лишние поля (passwords, internal ids, private flags)?
   - Логи не пишут PII / карточные данные / пароли?

5. DEPENDENCIES
   - Запусти `npm audit` / `pip-audit` / аналог — есть ли known CVE?
   - Нет ли подозрительных пакетов (typosquatting)?

6. RATE LIMITING & DOS
   - Дорогие операции — ограничены по частоте?
   - Загрузка файлов — есть лимит по размеру?
   - Тяжёлые запросы — есть таймаут?

7. CSRF / CORS
   - Мутирующие запросы защищены от CSRF?
   - CORS не `*` на чувствительных эндпоинтах?

Вывод: список находок с CVSS-like приоритетом [CRITICAL / HIGH / MEDIUM / LOW / INFO].
CRITICAL / HIGH — блокер перед мержем. Всё остальное — тикет в backlog.
```

## 15. Continuous Improvement — рост команды через наблюдение

**Когда:** в конце каждой сессии, перед рефлексией. Или отдельно — когда чувствуешь «что-то было неэффективно, но не успел записать».

```
Режим: ретроспектива сессии. Ты не пишешь код и не планируешь. Ты смотришь на то, что мы только что делали, и ищешь как нам вырасти.

Пройдись по 4 осям. Для каждой — дай ответ «есть/нет наблюдение» и, если есть, сформулируй предложение.

1. АГЕНТЫ (работа Claude / субагентов)
   - Был ли момент, где я ответил не то, что ты имел в виду?
   - Спавнил ли я субагента там, где хватало 1-2 tool-call?
   - Делал ли я Full Read крупных файлов вместо точечного?
   - Использовал ли я субагентов там, где надо было делегировать?
   - Какое правило в CLAUDE.md / AGENTS.md / prompts.md поможет не повторить?

2. ТОКЕНЫ / КОНТЕКСТ
   - Где контекст пробил 50%? 80%?
   - Что именно тянуло: какие файлы / Bash-выводы / цепочки Grep?
   - Пропустил ли ручной /compact на 50%?
   - Конкретный фикс: какое правило / hook / делегирование предотвратит повтор?

3. ПРОЦЕСС (Research → Spec → Plan → Code)
   - На какой стадии спотыкались?
   - Не хватило шаблона / gate / артефакта?
   - Handoff между сессиями сработал? Если нет — что добавить?

4. БИЗНЕС (факты про рынок/клиента/продукт)
   - Всплыл ли в разговоре факт о клиенте / рынке / юнит-экономике, которого нет в .business/?
   - Появилась ли гипотеза, которую стоит проверить?

ПРАВИЛА ВЫВОДА:
- Если наблюдение есть — сформулируй конкретное предложение (actionable, не «было бы неплохо»).
- Для каждого предложения — сразу создай файл в improvements/<категория>/YYYY-MM-DD-<slug>.md по шаблону из improvements/templates/.
- Если по оси наблюдений нет — напиши «0 наблюдений», не выдумывай.

НЕ делай:
- Не пиши общих советов («надо улучшить коммуникацию»).
- Не дублируй уже открытые идеи — сначала сверься с improvements/<категория>/.
- Не придумывай проблемы ради заполнения — лучше 1 конкретное наблюдение, чем 4 общих.

После прогона — короткий отчёт: сколько новых улучшений зафиксировано, в какие файлы.
```
