# Спека: тип счёта «Кредит» (детальный режим)

**Дата:** 2026-09-04 · **Ветка:** `feature/credit-account-type` (от `feature/deposit-detail-unified-card`, база `4c38a0e`)
**Макет:** [`2026-09-04-credit-account-type-mockup.md`](2026-09-04-credit-account-type-mockup.md) — утверждён владельцем
**Разведка:** [`2026-09-04-recon-schema.md`](2026-09-04-recon-schema.md) (схема, интеграции, тесты) · [`2026-09-04-recon-ui.md`](2026-09-04-recon-ui.md) (переиспользуемые компоненты)

## 1. Что делаем

Счёт-обязательство с полноценным договором: сумма, ставка, срок, тип и периодичность платежа,
график амортизации с разбивкой тело/проценты, досрочное погашение с выбором «срок или платёж»
и предпросмотром выгоды. Четыре экрана из макета: деталка · условия · график · лист досрочного.

Сегодня в проекте есть только «плоский» кредит: `AccountKind.loan` + embedded `LoanMeta`
(`principal/rate/monthlyPayment/paymentDay/termEnd/scheduleType/insurance`) — хранит условия,
но ничего не считает: ни графика, ни разбивки платежа, ни досрочного погашения.

---

## 2. Решения по схеме (приняты, не пересматриваются)

**Р1. Новых полей в `Account` / `LoanMeta` / `DepositMeta` — ноль.**
`LoanMeta` — composite attribute внутри `Account`; любое новое поле сдвигает checksum `Account`
задним числом во всех версиях V7–V11 → `NSCocoaErrorDomain 134504` на устройствах, где стор уже
создан. Урок зафиксирован в `AppSchemaFrozenGraphTests` (`millioTests/Core/Schema/`).

**Р2. Условия живут в новой таблице `@Model LoanContract`.**
Схема: `AppSchemaV12 = AppSchemaV11.models + [LoanContract.self]`, стадия
`.lightweight(V11 → V12)`, `typealias AppSchemaCurrent = AppSchemaV12`.
Декларации V1–V11 не трогаем, константы `stableEntityHashes` и `accountHashByVersion` не правим
(`LoanContract` попадёт в `stableEntityHashes` только когда V12 станет исторической, т.е. при V13).

**Р3. Связь с `Account` — по `accountID: UUID`, без `@Relationship`.**
Образец — `AccountAppearance` (`millio/Core/AccountsCore/Appearance/AccountAppearance.swift:16-24`)
и `AccountAppearanceStore.existingRows(for:)` (`:104-109`): `#Predicate` по `accountID` + upsert-хелпер.

**Р4. Тип счёта — существующий `AccountKind.loan`, нового kind не заводим.**
`.loan` уже относится к engine-классу «обязательство» (отрицательный итог не обрезается,
`AccountKind.swift:39`). Признак «детальный режим» = наличие `LoanContract` у счёта.

**Р5. `LoanMeta` — источник сида, не второй источник правды.**
Счёт `.loan` без `LoanContract` при первом открытии детального экрана получает `LoanContract`,
собранный из `LoanMeta` (backfill, read-only по `LoanMeta`). После этого все экраны кредита читают
только `LoanContract`; обратной синхронизации в `LoanMeta` нет. Резолвер `LoanTermsResolver`
(`LoanContract ?? LoanMeta`) — единственное место, где `LoanMeta` ещё читается.

**Р6. Фактический остаток долга = баланс счёта (лента `AccountEvent`), а не поле договора.**
Платёж и досрочное погашение — события на счёте, как начисления у вклада. Тогда:
`AccountTotalsContribution` править не нужно — `.loan` уже даёт отрицательный вклад в net worth,
и это ровно «остаток тела долга минусом, без будущих процентов» (согласовано с ремонтом кредитки
из `4c38a0e`: признак долга — данные счёта, а не догадка по kind).
График всегда строится от **фактического** остатка, поэтому журнал досрочек хранить не нужно
(см. Р8).

## 3. Модель `LoanContract`

```
@Model final class LoanContract: Persistable
  id: UUID                    // первичный
  accountID: UUID             // связь по id (Р3)
  principal: Decimal          // исходная сумма кредита — для прогресс-бара «из 1 200 000 ₽»
  annualRatePercent: Decimal  // 18.9
  termPeriods: Int            // исходный срок в ПЕРИОДАХ (60 при ежемесячной, 20 при квартальной)
  firstPaymentDate: Date
  scheduleTypeRaw: String     // annuity | differentiated
  frequencyRaw: String        // monthly | every2Months | quarterly | semiannual | annual
  paymentOverride: Decimal?   // ручной платёж из договора ИЛИ новый платёж после досрочки-«платёж»
  paymentsMade: Int           // сколько платежей внесено фактически
  paidInterestTotal: Decimal  // накопитель «уплачено процентов» (растёт при каждом платеже)
  insuranceAmount: Decimal?   // страховка — отдельная строка расхода, не часть платежа (UI отложен, см. §10)
  createdAt / updatedAt: Date
```

Все поля с дефолтами (требование SwiftData к аддитивной lightweight-миграции).
Доступ — `LoanContractStore` (`contract(for:)`, `upsert(accountID:mutate:)`) по образцу
`AccountAppearanceStore`.

`LoanTerms` — чистая value-struct (`Sendable`, без SwiftData): то же самое без `id/accountID/updatedAt`.
Вход расчётного ядра. `LoanContract.terms` отдаёт её, ядро о персистентности не знает.

## 4. Расчётное ядро

### 4.1 `LoanPaymentFrequency`

`monthly(1) · every2Months(2) · quarterly(3) · semiannual(6) · annual(12)` → `stepMonths`.
`AccountDepositCapitalization` **не расширяем** (чужая семантика, нет полугодовой/годовой).
Даты периодов — через существующий
`DepositInterestScheduler.scheduledPeriodEnd(openingDate:months:payoutDay:calendar:)`
(`millio/Core/AccountsCore/DepositInterestScheduler.swift:363`) с `months: stepMonths`;
он уже корректно обрабатывает короткие месяцы (31-е → 30/28).

### 4.2 `LoanScheduleEngine` — чистые функции

```
periodRate            = annualRate / periodsPerYear                (periodsPerYear = 12 / stepMonths)
annuityPayment(P,i,n) = P·i·(1+i)^n / ((1+i)^n − 1)
```

Строит `[LoanScheduleRow]`: `index · date · payment · interest · principal · balanceAfter`.
Дифференцированный: `principal = P / n` (константа), `interest = balance · i`, платёж убывает.
`paymentOverride` заменяет расчётный платёж; срок пересчитывается под него (число строк — пока
баланс > 0). Выходы: `outstandingPrincipal(after:)`, `interestAhead(from:)`, `totalOverpayment`,
`payoffDate`.

### 4.3 Контракт округления — **обязателен, проверен расчётом**

> Все вычисления — `Decimal` **без промежуточного округления**; платёж **не округляется** внутри
> модели; округление до рубля/копейки — только на отображении (`round2` из
> `DepositInterestScheduler.swift:379`, `.plain`).

Проверено на эталонном кредите: модель с округлённым платежом даёт остаток 1 137 239 и переплату
663 780 (расхождение с макетом 2–20 ₽), модель с точным платежом — 1 137 241 и 663 760, то есть
**все 12 контрольных чисел макета сходятся в ноль**. Это не стилистика, а условие приёмки Ф2.

### 4.4 `LoanPrepaymentPlanner`

Вход: текущий остаток, условия, сумма досрочного платежа (может быть и **недоплатой** — сумма
меньше планового платежа, тогда остаток уменьшается слабее и срок растёт). Считает два сценария
от одного и того же нового остатка `balance − amount`:

- **«срок»** — платёж прежний, число оставшихся платежей уменьшается; экономия = проценты впереди
  до минус проценты впереди после, **по фактическому графику** (не по закрытой формуле макета:
  владелец выбрал 226 771 ₽, а не 226 817 ₽);
- **«платёж»** — число оставшихся платежей прежнее, платёж = `annuityPayment(новый остаток, i, оставшихся)`.

Отдаёт `LoanPrepaymentPreview` для обоих: новый платёж · новая дата закрытия · проценты впереди ·
экономия · дельта числа платежей. Предвыбран «срок» (решение владельца).

### 4.5 Эталонные числа (юнит-тесты Ф2)

Кредит 1 200 000 ₽ · 18,9% годовых · 60 мес · аннуитет · ежемесячно:

| Проверка | Ожидание |
|---|---|
| Платёж | 31 063 ₽ |
| После 5 платежей: остаток / тело / проценты | 1 137 241 ₽ / 62 759 ₽ / 92 554 ₽ |
| 6-й платёж: проценты / тело | 17 912 ₽ / 13 151 ₽ |
| Переплата за срок | 663 760 ₽ |
| Проценты впереди после 5 платежей | 571 206 ₽ |
| Квартал / полгода: платёж (переплата) | 94 059 ₽ (681 174 ₽) / 190 704 ₽ (707 041 ₽) |
| Досрочно 200 000 ₽ → «платёж» | новый платёж 25 600 ₽, экономия 100 455 ₽ |
| Досрочно 200 000 ₽ → «срок» | 42 платежа вместо 55 (−13), экономия 226 771 ₽ |

переиспользуется как есть.

## 6. Экран 2 — условия кредита

Один компонент и на создание, и на правку: **все** условия редактируемые, включая сумму и ставку.
Read-only сумма и ставка из макета отменены 2026-09-04: у счетов из старого мира ставка нулевая
(старая форма её не собирала), а срок и сумма приезжают несогласованными — чинить их было бы нечем,
а от них зависит весь график. Тип платежа меняется и после создания — график перестраивается от
фактического остатка. Правка суммы догоняет остаток долга одним корректирующим событием, только
если по договору ещё не было платежей (`paymentsMade == 0`); иначе остаток остаётся за лентой (Р6).

Строки формы, тумблер, пикеры листом снизу — `AccountDetailsFieldRow` / `AccountDetailsToggleRow` /
`AccountFieldPickerSheet` (`DepositAccountDetailsSheet.swift:33/62/86`). Сегмент 2 опций —
нативный `.pickerStyle(.segmented)`. Все денежные поля — только `AmountTextField`.
Подсказка под ручным платежом показывает расчётную сумму («По формуле выходит 31 063 ₽…»).

## 7. Экран 3 — график платежей

Список строк «месяц · двухцветная полоса тело/проценты · сумма», текущий период подсвечен,
легенда, итоговая карточка «Переплата за весь срок» + доля от суммы кредита.
Двухцветная полоса — новый маленький компонент (аналога нет). Строк может быть до 60 —
рендер списком, без ленивой подгрузки.

## 8. Экран 4 — досрочное погашение (лист снизу)

Крупный ввод суммы (`AmountTextField`, рамп шрифта — `DepositAccountDetailsSheet.swift:540`),
две радио-строки «Срок / Платёж» с тегом выгоды у выгодного варианта, diff-таблица
«было → стало» (4 строки), карточка экономии, кнопка «Внести N ₽».
Радио-строка и diff-таблица — пишем (ближайший аналог `DepositCloseSheet.row`,
`DepositOperationSheets.swift:105`). Тот же лист обслуживает **недоплату** (сумма меньше планового
платежа): вместо экономии показывается рост срока/долга.

## 9. Интеграция (Ф7)

1. **Платёж → Cashflow.** Одна транзакция `.expense` на сумму платежа, образец —
   `DepositCashflowProjector.project()` (`:53-63`): `CashflowMonthMutationPolicy.validate` перед
   вставкой, дедуп через `importSourceRaw: "loanPayment"` + `importReferenceKey` = id платежа.
   Страховка — **отдельная транзакция**, не внутри платежа (решение владельца).
2. **Событие на счёте.** Тот же платёж уменьшает тело долга событием в ленте `AccountEvent`
   (проценты долг не уменьшают) → баланс счёта = остаток тела (Р6).
3. **Реестр моделей.** `ModelTypeRegistry.shared.register(LoanContract.self, typeName: "LoanContract")`
   + `LoanContractImporter` в `AccountsCoreFeatureRegistration.register()`
   (`AccountsCoreFeatureRegistration.swift:32,46`, образец — `AccountAttachmentImporter:66-89`).
   Round-trip тест бэкапа: экспорт → импорт не теряет полей договора.
4. **Net worth.** Правок `AccountTotalsContribution` не требуется (Р6) — но Ф7 обязана это
   **доказать тестом**: счёт `.loan` с остатком 1 137 241 ₽ уменьшает тотал ровно на эту сумму,
   будущие проценты в тотал не попадают.

## 10. Границы (в эту итерацию не входит)

- UI страховки (поле в модели есть, экрана нет) · плавающая ставка · кредитные каникулы ·
  штрафы и просрочка · напоминания о платеже в календарь · импорт графика из банка.
- Массовый перевод существующих `.loan`-счетов — только ленивый backfill при открытии (Р5).

## 11. Стиль и локализация

- `LoanScreenStyle` с accent `#E0A458` — по образцу `CashflowSurfaceStyle` / `CashbackScreenStyle`
  (в проекте у каждого сервиса свой accent, общего медного токена нет).
- Тело долга / проценты — существующие `AppColors.positiveColor` / `negativeColor`
  (макетные `#4FBF8B` / `#E4685D` — та же роль, отдельные токены избыточны).
- Отступы и шрифты — только `AppSpacing` / `AppTypography`. Dark Mode only.
- Строки — `Localizable.xcstrings` через `L()`; перед каждым коммитом
  `git diff --stat` по файлу (Xcode портит его при сборке на устройство).

## 12. Критерии приёмки

1. Схема: `AppSchemaV12` аддитивна, `AppSchemaFrozenGraphTests` и `SchemaConsistencyTests` зелёные,
   Account-checksum «10.0.0» не изменился, стор существующего пользователя открывается.
2. Ядро: все 12 эталонных чисел §4.5 сходятся в ноль, включая экономию 226 771 ₽ по графику.
3. Экраны собраны из переиспользованных компонентов; новых — только двухцветная полоса,
   радио-строка, diff-таблица, `LoanScreenStyle`.
4. Платёж создаёт транзакцию в Cashflow и уменьшает долг; повторный прогон не задваивает.
5. Тотал уменьшается ровно на остаток тела; будущие проценты в net worth не попадают (тест).
6. Гейт `make test`: без новых красных относительно базы `4c38a0e`.

| Риск | Мера |
