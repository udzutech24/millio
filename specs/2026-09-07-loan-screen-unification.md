# Спека: экран кредита — приведение к решениям владельца (Ф3 унификации)

План: [`plans/2026-09-07__account-screens-loan.md`](../plans/2026-09-07__account-screens-loan.md)
Предшественник: [`plans/2026-09-04__credit-account-type.md`](../plans/2026-09-04__credit-account-type.md) (Ф1–Ф7 ✅, в `develop`)

## WHY

Экран кредита построен раньше, чем владелец принял четыре решения (06.09). Три из них расходятся
с реализацией: платёж живёт фактом, а не планом; досрочка предвыбирает «срок»; страховка сидит
полем договора. Пока это не закрыто, кредит выпадает из бюджета и «Предстоящих», а лист досрочки
навязывает сценарий.

Спека **не описывает экран с нуля** — только целевое поведение по дельте. Что уже сдано и остаётся
как есть, перечислено в §5.

## 1. Платёж по кредиту = плановая операция Cashflow

**Инвариант: у активного кредита с договором всегда существует ровно одна незакрытая плановая
операция ближайшего платежа. Второго способа внести платёж нет.**

- При создании договора (`LoanContractStore.upsert`) заводится плановая операция расхода на
  `LoanScheduleEngine.regularPayment(terms:)` с датой `nextPaymentDate`, привязанная к счёту
  кредита, с `importSourceRaw: "loanPayment"`.
  - Периодичность из `LoanPaymentFrequency` мапится в `CashflowRecurrenceRule`:
    monthly→monthly, quarterly→quarterly, semiannual→semiannual, annual→yearly.
  - `every2Months` правила не имеет → ведётся **разовая** плановая операция на ближайший платёж,
    пересоздаваемая после каждого применения (открытый вопрос 1).
- Применение плановой операции (`CashflowScheduledService.applyDuePlannedTransactionsIfNeeded`)
  для операции с источником `loanPayment` обязано пройти через `LoanPaymentRecorder.recordScheduledPayment`:
  тело — в ленту счёта, проценты — в договор. Иначе расход спишется, а долг не уменьшится.
- Проектор `LoanPaymentCashflowProjector` **не создаёт вторую строку** для платежа, пришедшего из
  применения плана (дедуп по `importReferenceKey`).
- Кнопка «Внести платёж» на деталке = «применить ближайшую плановую операцию сейчас». Она не
  создаёт независимый платёж (открытый вопрос 2).
- Досрочка/недоплата, меняющие платёж или срок (`pinnedPayment`, смена `nextPaymentDate`),
  синхронизируют плановую операцию: сумма и дата обновляются, при закрытии кредита операция
  снимается.
- Удаление/архивирование счёта или договора снимает плановую операцию (без сирот).

**Крайние случаи:** кредит закрыт досрочно → операции нет; платёж применён в закрытом месяце
Cashflow → отбивается `CashflowMonthMutationPolicy` целиком, договор не трогается (порядок «Cashflow
первым» уже реализован в Ф7 плана 09-04); повторное применение → дедуп по `importReferenceKey`.

## 2. Лист досрочного погашения — без предвыбора

- Ни один вариант не выбран при открытии. Кнопка подтверждения неактивна, пока пользователь не
  выбрал вариант.
- У каждого варианта — своя **абсолютная** цифра выгоды («сэкономите N ₽»), а не разница между
  вариантами. Источник — `LoanPrepaymentPreview.savings` соответствующего сценария.
- Под цифрой выгоды — что меняется: «срок» → «−13 платежей, закрытие 03.2030»; «платёж» →
  «платёж 25 600 ₽ вместо 31 063 ₽».
- Один вариант (дифференцированный график, полное погашение, недоплата) → выбор не показывается,
  подтверждение сразу активно.

## 3. Страховка — вне кредита

- Поля страховки в UI кредита нет и не появляется.
- Проектор и recorder перестают порождать строку `.insurance`. `LoanContract.insuranceAmount`
  остаётся в модели как legacy-поле (схема V12 заморожена), но на поведение не влияет.
- Пользователь заводит страховку сам — обычной плановой операцией Cashflow.

## 4. Net worth

Без изменений: `.loan` отдаёт баланс ленты, лента содержит только тело. Подтверждено
`LoanNetWorthContributionTests`; фаза обязана оставить эти тесты зелёными.

## 5. Что остаётся как есть (сдано ранее, не переделываем)

Hero «Осталось выплатить» + прогресс + метрики 2×1 · чипсы условий (ставка / срок / тип графика,
ведут в «Условия кредита») · разбивка ближайшего платежа (тело / проценты) · переход «График
платежей · N впереди ›» с двухцветными полосами, подсветкой текущего периода и карточкой переплаты ·
форма условий в режимах создания и правки · медный акцент `LoanScreenStyle` · круглый ряд действий
и «···» листом снизу (Ф0) · зафиксированные расхождения с макетом Ф9a из журналов Ф3–Ф6 плана 09-04
(ядро считает фактическим графиком, макет — закрытой формулой; эталон — спека 09-04 §4.5).

## 6. Acceptance criteria

1. У кредита с договором в «Предстоящих» и в бюджете месяца видна операция платежа на сумму
   `regularPayment`, дата = ближайший платёж графика.
2. Применение этой операции уменьшает тело долга ровно на `principalPart` строки графика, проценты
   уходят в `LoanContract.paidInterestTotal`, в Cashflow ровно одна строка расхода.
3. Повторный прогон применения не задваивает ни транзакцию, ни событие ленты.
4. Досрочка со сменой платежа обновляет сумму плановой операции; полное погашение её снимает.
5. Лист досрочки открывается без выбранного варианта, подтверждение неактивно, у каждого варианта
   своя абсолютная экономия.
6. Ни один платёж не порождает строку `.insurance`.
7. Net worth кредита = остаток тела (существующие тесты зелёные).
8. `millioTests` в пределах baseline (2690–2720 passed / 18–28 failed, см. память по флакам),
   новых красных нет; `git diff --numstat Localizable.xcstrings` — только вставки.

## 7. Вне объёма

Добавление `every2Months` в общий `CashflowRecurrenceRule` · переделка макета графика ·
кнопка «отменить платёж» (откат баланса — известная незакрытая задача) · перенос страховки в
шаблоны Cashflow · мерж `feature/planned-operations-applied-notice`.
