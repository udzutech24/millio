# Spec: Единый продюсер серии для экрана «Динамика»

**Дата:** 2026-07-18
**План:** `plans/2026-07-18__dynamics-single-source-of-truth.md` (Фаза 1)
**Ветка исследования:** `feature/dynamics-double-count-fix` (HEAD `9629afb`; считается смерженной в develop — Q4)
**Тип:** L — архитектурное изменение тестированного ядра totals (правило 7 → stress-test обязателен, ниже).
**Статус:** SPEC (кода нет; реализация — Фазы 2–5 плана после явного «да» владельца).

## WHY

Сегодня на «Динамике» число «сколько у меня денег» и «на сколько изменилось» считается **тремя независимыми путями** над одними и теми же данными. Они клэмпят базу периода по-разному и не имеют инварианта связности → на экране цифры расходятся («+7099.6%» против «+146.8%», дубль даты на оси). Цель владельца: **один максимально простой источник истины**; заголовок, карточка и график — читатели одного массива, а не три калькулятора.

Подтверждённые пути (file:line, ветка `feature/dynamics-double-count-fix`):
- (a) **Заголовок-дельта** — `updateCurrentBalanceAndDelta` (`FinanceDynamicsViewModel.swift:804-904`) + `calculateDeltaPercent` (`:2444-2452`). `legacy calculateBalanceAtDate` + условный core через `accountsTotalsService.totalAt` (`:840-843`, только unscoped).
- (b) **График** — `updateChartDataAsync` (`:1492-1596`) → `buildTimeSeriesData` (`:1624-1913`, легаси-реплей) + `addingCoreContribution` (`:1611-1621`, core `totalAt` по-точечно, только aggregated).
- (c) **Карточка «Общая сумма»** — `FinanceDynamicsPresentation.totalRow` (`FinanceDynamicsPresentation.swift:12-39`), сумма `DynamicsBreakdownItem` из `legacyAccountDynamicsRows` (`:1263-1377`) + `coreAccountDynamicsItems` (`:1191-1237`).

## Ponytail-вердикт по гипотезе `seriesBetween`

**Гипотеза (из плана):** сделать `AccountsTotalsService.seriesBetween` (`AccountsTotalsService.swift:76-88`) единственным продюсером серии.

**Вердикт: ОТКЛОНЕНА как «sole producer». Легаси-реплей ещё нужен.**

Доказательство:
1. `seriesBetween`/`totalAt` суммируют **только счета нового ядра** (`FetchDescriptor<Account>`, `AccountsTotalsService.swift:40,60,77`). Легаси-мир (`FinanceAccount` + `Card`/`Credit`/`Investment`/`Cashflow`-транзакции) в ядро **не портирован** — 53 ссылки на легаси-модели в `FinanceDynamicsViewModel`; `buildTimeSeriesData` реально реплеит легаси-баланс через `calculateBalanceAtDate` (`:1624-1913`), а `addingCoreContribution` лишь **добавляет** core поверх (`:1611-1621`).
2. `seriesBetween` в коде **не вызывается ни разу** (grep: только `totalAt`/`total(for:on:)`). Значит core-серия сейчас собирается по-точечно тем же `totalAt`, что и продюсер соберёт — переход на `seriesBetween` даёт лишь курсорный сахар, не меняя результата.

**Минимальный продюсер (принятый вариант — рунг «переиспользуй существующее»):** один метод строит per-day массив, складывая **легаси-реплей (`calculateBalanceAtDate`) + core-вклад (`totalAt`) ОДИН раз на календарный день**; заголовок и карточка читают его концы. Новый слой/сущности не заводим. `seriesBetween` при желании используем как обёртку для core-части (эквивалент текущему `addingCoreContribution` по значению), но это не обязательно и не является источником истины для легаси. Порт легаси на ядро (тогда `seriesBetween` стал бы sole producer) — **вне скоупа** (YAGNI до отдельной инициативы «1b»).

## WHAT — контракт продюсера

Один `@MainActor async` метод во `FinanceDynamicsViewModel`:

```
func dynamicsSeries(for scope: DynamicsScope) async -> DynamicsSeries

struct DynamicsSeries {
    let periodStart: Date          // фактическое начало периода (НЕ клэмпится к дате создания)
    let periodEnd: Date
    let points: [DataPoint]        // ≥2 точки, по одной на календарный день события, отсортированы
}
struct DataPoint { let day: Date; let value: Double }   // value = легаси-реплей + core, суммарно, в displayCurrency
```

### Правила

1. **База периода НЕ клэмпится (Q2).** Первая точка = на `periodStart` запрошенного периода (1D/1W/1M/1Y/All). Счёт, созданный **после** `periodStart`, до своего `createdAt` даёт **0** (не «виртуальный ноль задним числом», но и не клэмп диапазона к `firstDataDate`). Это требует **убрать** клэмп `max(requestedPeriod.start, firstDataDate)` в `resolvedPeriodDates` (`:1928`) — период держит запрошенную ширину, дельта честно включает появившиеся на счёт деньги.
2. **Архивные включены (Q3).** База периода и история считаются с учётом archived-счетов: `participatingOnly` для базы истории учитывает архив (архивация не переписывает прошлое). Период (диапазон) и раньше считался по всем счетам, включая archived (`:808-810`) — сохраняем.
3. **Дедуп точек по календарному дню.** `eventDates` (`:1665-1743`) сейчас `Set<Date>` по exact-`Date` → один день с разным временем = две точки на оси (находка 4). Продюсер нормализует каждую дату к `startOfDay` (Gregorian) перед вставкой; на день — одна точка.
4. **Единый `resolvedPeriodDates` для заголовка И графика.** Заголовок (`:811`) и график (`:1508`) обязаны вызывать один и тот же расчёт периода на одном наборе счетов → одинаковые endpoints (закрывает находку 3).
5. **Заголовок-дельта = чистая функция массива:** `delta = points.last.value − points.first.value`; `percent = calculateDeltaPercent(delta, startBalance: points.first.value)`.
6. **Карточка `totalRow` = те же endpoints:** `startValue = points.first.value`, `endValue = points.last.value`, `delta` — та же. Никакого повторного `reduce` над breakdown для aggregate-строки Total.
7. **Легаси + core складываются один раз на день** внутри продюсера (не дважды — устраняет double-count-класс).

Scoped-режимы (выбор групп/счетов, single-account) остаются на легаси-пути per-account до порта «1b» — продюсер обслуживает **unscoped aggregate** (заголовок/карточка/график общего тотала), где и живут расхождения. Для scoped Total карточка продолжает агрегировать per-account строки тем же знаковым правилом (`signedAccountValue`), но её endpoints обязаны совпасть с суммой соответствующих per-account серий (инвариант в тесте, Фаза 4).

## Что удаляется / сворачивается (file:line)

При переходе на продюсер удаляются параллельные recompute-пути (боль, не красота — реальные источники расхождения):

- `updateCurrentBalanceAndDelta` (`FinanceDynamicsViewModel.swift:804-904`) — заменяется чтением `points.first/last` из продюсера (для unscoped); scoped-ветка (single-account) ужимается.
- `addingCoreContribution` (`:1611-1621`) — сворачивается в продюсер (core складывается внутри цикла построения ряда).
- Отдельный `reduce` для aggregate-Total в `FinanceDynamicsPresentation.totalRow` (`FinanceDynamicsPresentation.swift:12-39`) — Total-строка берётся из endpoints продюсера; `totalRow` остаётся только для scoped per-account суммирования (или удаляется, если scoped Total тоже переведён на серию).
- Клэмп базы в `resolvedPeriodDates` (`:1928`) — удаляется (Q2).
- Дубль-логика процента: `calculateDeltaPercent` (`:2444-2452`) остаётся ЕДИНОЙ функцией, её копии в `totalRow`/`aggregateGroupRows`/`coreAccountDynamicsItems` (`FinanceDynamicsPresentation.swift:25`, `:1383-1434`, `:1191-1237`) убираются в пользу вызова.
- `buildTimeSeriesData` (`:1624-1913`) — НЕ удаляется (легаси-реплей нужен), но становится внутренностью продюсера: его выход дедуплится по дню и складывается с core до возврата массива.

`AccountsTotalsService.seriesBetween` — **не трогаем** (может остаться неиспользованным; удаление — отдельный ponytail-cleanup, не в этой линии).

## Non-goals

- Порт легаси-мира (`FinanceAccount`/`Card`/`Credit`/`Investment`) на AccountsCore — отдельная инициатива «1b».
- Soft-delete/tombstone для `AccountDailySnapshot` (Q1) — это **Фаза 5** плана, не входит в контракт продюсера (продюсер лишь потребитель истории; корректность базы удалённых счетов обеспечивает Ф5).
- Инвариант тотала «Счета» vs Активы/Обязательства (находка 5) — отдельная задача (YAGNI).
- Изменение per-account scoped-графика (режим одного счёта, выбор групп) — остаётся на легаси-пути.

## Acceptance criteria

- **AC1 (главный инвариант).** Для КАЖДОГО периода (1D/1W/1M/1Y/All) в unscoped-режиме: `заголовок.delta == (points.last.value − points.first.value) == (карточка.endValue − карточка.startValue)`, с точностью до копейки. Тест — Фаза 4.
- **AC2.** Ось графика не содержит двух точек одного календарного дня (дедуп по `startOfDay`).
- **AC3 (Q2).** Счёт создан внутри периода → `points.first.value` включает 0-вклад этого счёта (не клэмпит `periodStart` к его `createdAt`); дельта = фактически появившиеся деньги. Период сохраняет запрошенную ширину.
- **AC4 (Q3).** Archived-счёт присутствует в базе периода и в исторических точках; архивация после факта не меняет прошлые точки.
- **AC5.** Легаси-only портфель (нет core-счетов): продюсер = чистый легаси-реплей, поведение не регрессирует (core-вклад = 0).
- **AC6.** Core+легаси портфель: значение точки = легаси + core, каждое слагаемое учтено ровно один раз (нет double-count).
- **AC7 (регрессия ядра totals).** Значения `points` в unscoped-режиме на любую дату сходятся с `AccountsTotalsService.totalAt` для core-части (ядро totals не искажено интеграцией).

## Stress-test (10 причин провала)

Прогон по этой спеке (правило 7; изменяется тестированное ядро totals). Формат: проблема · вероятность · митигация.

1. **Безопасность.** Продюсер не трогает credentials/Keychain/бэкап — читает уже загруженные модели. **Низкая.** Митигация: не нужна; смена — чисто вычислительный слой UI.
2. **Нагрузка / производительность.** Продюсер зовёт `totalAt` (реплей) на КАЖДЫЙ event-день; период All × большой портфель = O(days×accounts) с реплеем. **Средняя.** Митигация: строить точки только на **event-дни** (не на каждый календарный день — как сейчас `eventDates`), тёплый снапшот-кэш `rebuilder` → no-op (`AccountsTotalsService.swift:92-94`); замерить на реальном портфеле Алексея до Ф4; при деградации — `ponytail:` комментарий с планом батч-фетча снапшотов.
3. **Юридика/compliance.** Данные не собираются/не отправляются — локальный расчёт. **Низкая.** Митигация: не нужна.
4. **Функционал / граничные значения.** Пустой период, портфель без счетов, один event-день (график требует ≥2 точки), все счета archived, счёт создан ПОСЛЕ periodEnd, отрицательные балансы (кредиты), нулевая база при проценте (деление на 0). **Высокая.** Митигация: явные guard'ы (`points` всегда ≥2 через синтетические start/end как в `:1638-1662`); `calculateDeltaPercent` уже гейтит `abs(start)>0.01` (`FinanceDynamicsPresentation.swift:25`); тест каждого кейса в Ф4.
5. **Кросс-платформа / устройство.** Расчёт тяжелее на слабом устройстве (реплей в цикле); блокировка MainActor при длинной серии → фриз UI. **Средняя.** Ветка исследования — MainActor. Митигация: сохранить `Task.isCancelled`-чеки (`:805,852,879`) и генерацию-стемпинг (HEAD `9629afb` — монотонная публикация тоталов); длинный реплей уже вне главного sync-пути (async).
6. **Данные / потеря.** Продюсер только читает. НО удаление счёта каскадит `AccountDailySnapshot` (`Account.swift:36`) → база истории «уезжает». **Высокая (но вне скоупа продюсера).** Митигация: это корневой баг, закрывается **Ф5** (soft-delete, Q1); продюсер обязан читать историю с учётом tombstone после Ф5. Спека продюсера НЕ должна закрывать Ф5 сама — зависимость зафиксирована.
7. **Стоимость.** Нет внешних API в расчёте (курсы — из кэша `rateService`, историч. курс на дату). Риск: `getHistoricalRate` на каждый день × валюта. **Низкая-средняя.** Митигация: курс уже кэшируется; серия по event-дням, не по всем дням, ограничивает число запросов.
8. **UX.** После правки заголовок и карточка станут ВСЕГДА равны — если раньше пользователь «привык» к расходящимся числам, изменение корректно, но график с не-клэмпнутой базой (Q2) покажет плоский 0-хвост до создания счёта — может выглядеть непривычно. **Средняя.** Митигация: Q2 — прямое решение владельца (честная база = 0); задокументировано; при желании — тонкая линия/подпись «счёт создан N».
9. **Зависимости.** Продюсер зависит от `financeViewModel.accountsTotalsService` и `rebuilder`/`marketPriceService`. Если core-сервис недоступен (не сконфигурирован в тестах) — `marketPriceService` опционален (`AccountsTotalsService.swift:15`), `totalAt` вернёт 0 при отсутствии счетов (`:40`). **Низкая.** Митигация: контракт «core-вклад = 0 при отсутствии ядра» уже соблюдён; тест AC5 покрывает.
10. **Слепое пятно.** Scoped-режимы (группы/single-account) НЕ обслуживаются продюсером и продолжают жить на легаси-пути → инвариант AC1 действует только для unscoped; в scoped Total карточка всё ещё может разойтись с per-account суммой (остаточный класс находки 5-подобный). **Средняя.** Митигация: явный non-goal + AC для scoped Total как «сумма per-account серий == endpoints карточки»; если полное покрытие scoped потребуется — отдельная фаза, не расширять текущую (YAGNI).

### Отдельно: риск для протестированного ядра totals (правило 7)

`AccountsTotalsService` покрыт тестами (финальный гейт 29/29, «единый источник totals»). Продюсер его **не модифицирует** — только вызывает существующие `totalAt`/`total(for:on:)`. Риск регрессии ядра — **низкий**: интеграция аддитивна (сложение легаси+core в UI-слое), сигнатуры сервиса не меняются. Единственная точка касания ядра в этой линии — **Ф5** (cascade → soft-delete в `Account.swift`/`AccountDailySnapshot`), которая ДЕЙСТВИТЕЛЬНО трогает модель ядра и потребует своего stress-test + `AskUserQuestion` перед реализацией (не в этой спеке). Вывод: Фазы 2–4 (продюсер) — низкий риск для ядра; Фаза 5 — отдельный гейт.
