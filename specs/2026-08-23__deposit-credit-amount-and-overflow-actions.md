# Spec: изменение суммы вклада/долга и overflow-действия

## Problem

Экран вклада перегружен редкими и destructive-действиями, но не даёт пользователю исправить сумму. На вкладах нельзя использовать общий balance-adjustment без пересчёта будущих процентов. На кредитной карте второстепенные редактирование и удаление занимают место рядом с регулярными финансовыми действиями.

## Goal

Сделать изменение текущей суммы безопасной, журналируемой операцией для активных вкладов и сохранить быстрое изменение суммы долга кредитной карты. Оставить на экране только частые денежные операции, а редкие/опасные перенести в `…` в шапке.

## Acceptance criteria

- [ ] Активный или бессрочный вклад показывает `Изменить сумму`; действие открывает форму с текущей суммой и датой корректировки.
- [ ] Сохранение новой суммы вклада создаёт одно append-only `adjustment`-событие на дельту, не редактирует старые события и в одной транзакции пересчитывает generated forecast после даты корректировки.
- [ ] Повторное сохранение исходной суммы не создаёт пустого события.
- [ ] Закрытый, созревший и incomplete-вклад не показывает и не принимает изменение суммы.
- [ ] Основные кнопки вклада — только `Пополнить` (когда доступно) и `Изменить сумму`; `Изменить условия`, `Закрыть досрочно`, действие по сроку и `Удалить` доступны из `…` в шапке при соблюдении текущих capability/lifecycle-ограничений.
- [ ] У кредитной карты `Изменить сумму долга` остаётся доступной как основное финансовое действие; редактирование данных карточки и удаление доступны из `…` в шапке.
- [ ] Досрочное закрытие и удаление по-прежнему требуют текущих подтверждений; перенос в меню не позволяет обойти safeguards.
- [ ] Новая бизнес-логика покрыта unit-тестами; presentation-тесты фиксируют состав primary/overflow-действий.
- [ ] Переход к другому типу продукта открывается отдельным полноэкранным экраном в визуальном языке Millio, а не системным menu-popover поверх формы; выбор типа представлен компактными карточками/строками с понятным текущим состоянием.
- [ ] В форме условий вклада явно задаётся день начисления процентов для ежемесячной и ежеквартальной капитализации; переход типа продукта не сбрасывает этот день в `nil`.
- [ ] При включении досрочного закрытия потеря процентов по умолчанию равна `0 %`; поле имеет видимую подпись, крупное значение и валидный диапазон `0…100`.
- [ ] Изменение суммы вклада остаётся отдельной операцией из фазы 1, а не полем в форме условий: это исключает частичное сохранение двух разных финансовых команд.
- [ ] В формах условий и смены типа верхняя панель содержит только кнопку закрытия; единственная primary CTA внизу экрана (`Изменить условия` / `Изменить тип`) учитывает клавиатуру и активна лишь при валидных данных.

## Scope

- iOS SwiftUI account detail для вкладов и кредитных карт.
- Deposit coordinator, presentation model и точечные локализованные строки, если существующих недостаточно.
- Unit tests и визуальная проверка iPhone-размеров/Dynamic Type.
- Редизайн формы условий вклада и выделенного маршрута смены типа продукта.

## Non-goals

- Частичное снятие вклада.
- Изменение банковских условий или начислений задним числом.
- Переработка действий всех остальных типов счетов.
- Изменение серверного API, CloudKit-схемы или миграция данных.
- Совместное сохранение изменения суммы и условий одним действием.

## Constraints and risks

Ключевое ограничение — прогноз процентов вклада зависит от суммы. Нельзя вызывать общий `adjustBalance` без нового coordinator-route, потому что он не пересобирает schedule. Подтверждённые банковские interest-события immutable; пересчитываются лишь generated future events. Сумма должна быть неотрицательной, а новый баланс, равный текущему, является no-op.

Системный `Picker(.menu)` для длинного списка типов и капитализации не проходит UX-критерий: он скрывает контекст, накладывается на контент и плохо работает на малом экране с клавиатурой. Его заменяет route/selector в визуальном стиле приложения. Для капитализации без начислений день выплаты не показывается; для ежемесячной/ежеквартальной — обязателен и ограничен диапазоном `1…31` с корректным переносом на последний день короткого месяца, который уже обеспечивает scheduler.
