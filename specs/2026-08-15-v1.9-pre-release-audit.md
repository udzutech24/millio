# Spec: Millio 1.9 pre-release audit

## Problem

A green build alone cannot prove that version 1.9 is safe to ship, especially when restore can replace user data and depends on CloudKit, encryption and schema compatibility.

## Goal

Produce a reproducible GO / CONDITIONAL GO / NO-GO decision backed by commands, logs and real scenario evidence.

## Acceptance criteria

- [ ] Baseline records branch, commit, worktree, version/build, deployment target, devices, signing and TestFlight 1.9 (10) state.
- [ ] Backup/Restore matrix covers local/cloud, automatic/manual, clean/replace restore, password failures, corrupt/empty/incompatible/legacy data, integrity-before-delete, ownership, logout/login and repeat-restore semantics.
- [ ] Critical product flows have explicit evidence or are marked blocked/not run.
- [ ] All selectable locales pass key/placeholder/format/leak checks and new Backup/Cashflow/Upcoming UI is visually inspected.
- [ ] Unit, integration and relevant UI suites run with captured outcomes.
- [ ] Release build/archive, signing, entitlements, privacy manifests, permissions, secrets/debug artifacts and warnings are audited.
- [ ] A connected physical iPhone result is recorded.
- [ ] App Store assets, metadata, identifiers, build train and Apple validation are recorded.
- [ ] Unknown or unexecuted production checks cannot produce GO.
- [ ] Any code fix is preceded by proof and waits for the required implementation guard phrase.

## Scope

Read-only audit, test/build artifacts, audit documentation and evidence. Safe simulator data may be created and reset. Existing user files are preserved.

## Non-goals

No commit, push, merge, upload, TestFlight/App Store submission, production data deletion, CloudKit mutation or code implementation without separate authorization.

## Constraints and risks

Physical-device and production-service checks require valid accounts/signing/network. Restore is destructive unless executed against isolated test data and must validate backup integrity before replacement.
