# Workflow-промпт

Вставляй в начале любой новой задачи. Он сам определит размер, выберет нужный путь и проведёт через все стадии.

---

```
Мы начинаем работу над задачей. Прочитай CLAUDE.md и AGENTS.md — они рамка. Не меняй правила.

ЗАДАЧА: [опиши одной фразой]

───────────────────────────────────────────────────────────
ШАГ 0. ПРАВИЛА СЕССИИ (действуют всегда)
───────────────────────────────────────────────────────────

1. Контекст ≤ 50% — на 50% делаешь ручной /compact, не ждёшь автокомпакта.
2. Research → только sub-агенты с саммари ≤ 200 слов. Не вываливай кодбазу.
3. Read — только нужные файлы. Grep → Read(offset/limit ±50 строк). Full Read запрещён для файлов >500 строк.
4. Код не пишешь до триггер-фразы «Реализуй фазу N по плану» — до этого только чтение, вопросы, планы.
5. Каждый вопрос — с рекомендацией. Не скидывай выбор без обоснования.
6. Если что-то неэффективно по ходу (лишние Read, токены, промах агента) — фиксируй сразу в improvements/.

───────────────────────────────────────────────────────────
ШАГ 1. КЛАССИФИКАЦИЯ
───────────────────────────────────────────────────────────

Определи размер задачи и скажи мне — жди подтверждения перед продолжением:

- S: багфикс или правка 1-2 файлов → иди в ПУТЬ S
- M: новая фича или рефактор 3-10 файлов → иди в ПУТЬ M
- L: архитектурное изменение или 10+ файлов → иди в ПУТЬ L

Если не уверен — задай уточняющий вопрос через AskUserQuestion с вариантами.

═══════════════════════════════════════════════════════════
ПУТЬ S — Быстрый (багфикс / мелкая правка)
═══════════════════════════════════════════════════════════

S-1. ДОКАЖИ БАГ
Прежде чем что-то менять: опиши конкретный сценарий воспроизведения — вход → ожидание → реальное поведение.
Если не можешь воспроизвести — это не баг. Не трогай код.

S-2. МИНИМАЛЬНЫЙ ПЛАН
Один абзац: что именно меняешь, какие файлы, почему.
Нет плана — нет кода. Жди «Реализуй».

S-3. РЕАЛИЗАЦИЯ (только после «Реализуй»)
Меняй только то, что в плане. Ни строкой больше.

S-4. SELF-AUDIT
После правки — сверься: баг устранён? Ничего лишнего не изменил? Тесты зелёные?

S-5. РЕФЛЕКСИЯ
Создай .business/история/YYYY-MM-DD-<название>.md по шаблону templates/reflection.md.
Зафикируй в improvements/ если что-то заметил.

═══════════════════════════════════════════════════════════
ПУТЬ M — Стандартный (новая фича / рефактор)
═══════════════════════════════════════════════════════════

M-1. RESEARCH (только чтение)
Запусти Agent(subagent_type=Explore) для изучения кодбазы.
WebSearch: кто уже решал эту проблему? Лучшие практики?
Сохрани артефакт в thoughts/research/YYYY-MM-DD-<slug>.md.
Артефакт обязан заканчиваться разделом «Рекомендация» — какое решение лучшее и почему.
Жди моего ОК перед переходом к спеке.

M-2. SPEC
Создай specs/YYYY-MM-DD-<slug>.md по шаблону templates/spec.md. Заполни:
- Problem / Goal / Scope / Non-Goals
- Acceptance Criteria (проверяемые, конкретные)
- Constraints
Жди ОК — я могу добавить NOTE-комментарии, отработай их все перед переходом к плану.

M-3. PLAN + CHALLENGE LOOP
Создай plans/YYYY-MM-DD__<slug>.md по шаблону templates/plan.md.
Разбей на фазы. Для каждой: что делаем, какие файлы, acceptance criteria.
Обязательно пропиши Edge Cases (думай вперёд: null, 100x нагрузка, конкурентность, откаты).

Challenge Loop — ответь на 3 вопроса в плане (Challenge Log):
1. Каждый пункт плана покрывает acceptance criteria из спеки?
2. Это самое эффективное решение? (2-3 альтернативы с +/–, выбор с обоснованием)
3. Есть ли в плане «код ради кода»? Если да — удали.

Жди «Реализуй фазу N по плану» — до этого код не пишешь.

M-4. РЕАЛИЗАЦИЯ (фаза за фазой)
Только та фаза, которую назвал я. После каждой фазы — Self-Audit:
- Все acceptance criteria фазы покрыты? (файл:строка для каждого)
- Нет кода вне scope?
- Тесты зелёные?
Говори «Фаза N завершена» только если всё ОК. Жди следующей команды.

M-5. IMPACT ANALYSIS (перед мержем)
1. Регрессия — что зависит от изменённых файлов? Все тесты зелёные?
2. Side effects — изменились контракты/API/типы? Все потребители обновлены?
3. Edge cases — что будет при нулевых / огромных данных / конкурентных запросах?
4. Совместимость — нужны ли миграции? Feature flag?

M-6. CODE REVIEW
Посмотри на diff как reviewer, не как автор:
- Каждый acceptance criterion покрыт?
- Нет «кода ради кода», магических констант, мутных имён?
- Тесты проверяют поведение, а не реализацию?
Вывод: BLOCKER / MAJOR / MINOR / NITPICK. BLOCKER и MAJOR — блокируют мерж.

M-7. РЕФЛЕКСИЯ + CI
Создай .business/история/YYYY-MM-DD-<название>.md по шаблону templates/reflection.md.
Прогони промт #15 по 4 осям (агенты / токены / процесс / бизнес).
Для каждого наблюдения — файл в improvements/<категория>/.
Актуализируй план: статус, фазы [x], журнал.

═══════════════════════════════════════════════════════════
ПУТЬ L — Полный Bulletproof (архитектура / 10+ файлов)
═══════════════════════════════════════════════════════════

L работает как путь M, но с дополнительными условиями:

L-0. РАЗБИВКА НА СЕССИИ
Задача L не делается в одном чате. Обсудим разбивку на сессии до старта:
- Сессия 1: Research → Spec (handoff в progress/)
- Сессия 2: Plan + Challenge Loop (handoff)
- Сессии 3-N: Phased Implementation (handoff после каждой фазы)
- Финальная: Impact Analysis + Code Review + Security Scan + Reflection

L-SECURITY SCAN (обязательно перед мержем, если есть auth / user data / внешние API / SQL):
Проверь по OWASP Top 10: input validation, auth/authz, secrets, data exposure, dependencies, rate limiting, CSRF/CORS.
CRITICAL / HIGH — блокер. Остальное — тикет в backlog.

L-HANDOFF между сессиями:
Перед /clear создай progress/<task>-handoff.md по шаблону templates/handoff.md.
В новой сессии начинай с чтения этого файла — не пересказывай всё заново.

───────────────────────────────────────────────────────────
ПОСЛЕ ЛЮБОГО ПУТИ
───────────────────────────────────────────────────────────

Без этих трёх шагов чат не считается завершённым:
1. Рефлексия в .business/история/YYYY-MM-DD-<название>.md
2. Актуализация плана (статус, фазы, журнал)
3. improvements/ — хотя бы «0 наблюдений» по каждой оси

───────────────────────────────────────────────────────────

Начинай с ШАГ 0 (правила сессии) → ШАГ 1 (классификация).
После классификации жди моего подтверждения перед продолжением.
```
